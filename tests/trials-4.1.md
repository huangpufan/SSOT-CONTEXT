# 4.1 decision authority, recovery and review trials

The user-facing question was whether adopting SSOT preserves decisions people already accepted, distinguishes them from proposals and implementation drift, and repairs incomplete records without inventing approval. A related question was whether an explicit SSOT review still runs when followed by implementation, while ordinary code review and a pure command avoid unnecessary Doctor work.

In the completed authority Round 3, the candidate ran the requested Doctor scope, registered an existing formal decision as confirmed, implemented an already accepted partial replacement, preserved the remaining protection, and stopped a different request whose loss had not been accepted. The 4.0 baseline implemented the replacement but reverted its register wording after a checker error, leaving a contradiction despite a passing checker. Three candidate-only controls made no file changes and did not invoke Doctor. Later native Codex cases observed immediate save → actual readback → dependent writing, an independent checkpoint handoff and a read-only control; their model request and evidence limits are described separately below.

This is not a completed real-project adoption or a general reliability result. One real bootstrap run stopped at its one-hour cap without a README; a later run also reached the cap, but left a useful partial README and an unfinished empty register. A subsequent real installation completed with readback and a final result. The next completion run has continued through three deliberate review interruptions and same-session corrective resumes. It remains in progress; correction-prompt effects are not blind protocol evidence. Checker recovery and a later mixed-clause fixture produced inspectable state/artifact results but timed out before final responses.

## Authority, dates and the false-green result

An existing formal owner can preserve a human-established decision even when its original exchange was not supplied. This is different from a filename, an unreviewed assistant summary, a description of current behavior or a pending proposal. The trials keep these cases separate. They also distinguish an accepted decision from current implementation: later code that puts progress first or routes an internal limitation to the user does not authorize replacing U12 or U13.

The baseline false-green sequence is concrete. In Rounds 2 and 3 it updated the register's pagination wording without updating Source. The checker rejected the changed confirmed row. The baseline then restored the old pagination wording to remove that error, while code and the formal T1 record still said incremental loading. A passing structural check therefore coexisted with a material contradiction. Candidate Round 3 updated both the authorized clause and its formal Source instead. Two baseline observations establish this counterexample, not a frequency or inevitability.

The later recovery fixture enters that same incomplete-record state directly. Both positive arms use the latest shared protocol; only the checker diagnostic differs. T1's acceptance and original record dates are unknown, with no original chat or verbatim answer. The new-diagnostic subject first added the formal T1 citation without a new date, still received ERROR, then wrote:

> 2026-11-06 is only the date of verifying this source record, not its approval date and not what determines replacement order.

The actual saved wording is Chinese with that meaning. Its date matches the run. The checker then passed while the approval date remained unknown and the accepted behavior stayed unchanged. The proposal control restored the old protection instead of adding a date to legitimize an unaccepted change. This tests a transition through a real error, rather than only a final well-formed document.

The checker algorithm did not gain an acceptance oracle. Its entire module AST is identical between the diagnostic arms after normalizing only `report.add` message arguments; Source/date checks, control flow and severity remain. A new date remains a recording guard, not proof of human approval. The old-diagnostic recovery arm did not finish, so this experiment cannot attribute a general improvement to the new text.

## Structural reasoning exploration: what it found and what it did not prove

The separate mathematical discussion considered lifecycles, ownership graphs, sets/mappings, constraints and counterexamples as ways to find missing relationships. `math-discussion.json` records a completed Sonnet discussion, not an experiment establishing every recommendation. In particular, its suggested `3/n` omission bound, a helper per entity, arbitrary state limits and proposed replacements for existing mining are not established by the evidence and are not trial conclusions. Correlated model judgments and a modeler's chosen case set do not justify a statistical completeness bound.

A read-only probe then used an explicitly fixed historical consumer revision N0, rather than current code or the expected answer. It separated the accepted stable-notification-identity contract from engineering delay values and observed implementation. The useful finding was a cross-owner identity mismatch: recording the same continuing blocker again creates a new stage-event identity, and notifications derive identity and the waiting-time origin from that newest event.

With byte-for-byte exported notification modules, Node 24.15.0's in-memory SQLite and synthetic event inputs, the probe observed two sequences. Repeating the unchanged wait at minutes 5 and 10 left no claim at minute 15 because the timer restarted at minute 10. After a successful delivery at minute 15, repeating the same wait at minute 16 produced a different eligible tag at minute 31. A control that changed only the latest-report fixture retained the expected minute-15 claim: existing test intent could therefore pass while missing the actual event-producing boundary.

A later readback at separately fixed revision N1 reproduced both local sequences. N0 and N1 are portable case labels; their private source commit identities and exported-file hashes remain in the local manifests. A separate sent-receipt terminal-state change in that version did not repair identity or timing. Neither probe ran real Batches/Matters transactions, a browser or production data. Static reachability plus an isolated SQLite reproduction is not business end-to-end proof, a production incidence estimate or a product fix.

A third fixed revision, N2, had the same five relevant module files as N1. Reusing the unchanged probe reproduced the same two counterexamples and control output. This updates the fixed-version readback, not the set of covered transitions or the production evidence level.

The SSOT lifecycle analysis in `ssot-state-coverage.md` applies the same discipline to SSOT itself. It keeps installation, new-session discovery and invocation separate; source discovery, reading and reconciliation separate; recorded acceptance and original-source verification separate; decision, implementation and one-run observation separate; and checker structure separate from truth. This explains the observed false-green counterexample and identifies still-unobserved paths. Its snapshot predates the recovery result above and the real bootstrap's final time cap; those later observations update the relevant limits here, without rewriting the old analysis.

The subsequent 500-word `structural-review.md` reference puts scoped lifecycle, ownership, mapping and counterexample prompts into existing Doctor/mining roles. It is a later source change than the native Round 3 body. The probe supports a specific useful method example; there is no same-budget native comparison of that final integration, no proof it improves all mining, and no reason to use product test totals as the denominator of SSOT coverage.
