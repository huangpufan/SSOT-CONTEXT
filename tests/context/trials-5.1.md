# Native continuation and source handoff evidence for 5.1

This report asks whether an installed agent can preserve and use maintained context across task boundaries, and whether source admission actually governs owner writes. It also tests an 80-rule development register before considering a different reading policy. The coordinator's [evolution review](../../docs/evolution-review-2026-11-12.md) owns design decisions and rejected alternatives; this report owns the observations and their limits.

All native subjects request and report `gpt-6.1-terra`, medium effort, through Codex 0.167.1. At most two subjects run concurrently in isolated workspaces. The installed cases use the official installer, real catalog discovery and project instructions; each continuation phase has a fresh native home and session but shares the saved workspace. C06 compares protocols through the same frozen connector. No model calls run in CI. The [result inventory](results/context-evolution-5.1-2026-11-12.json) preserves frozen source, fixture and harness identities, native receipt hashes, all attempts and costs. Raw streams remain task-local under the inventory's `/tmp` paths; they are not a public transcript archive.

## Acceptance and observation boundary

The continuation must retain accepted research methodology, narrow only the corrected creative permission, preserve originals and uncertainty, leave context untouched during the unrelated typo, and apply the maintained knowledge to a concrete final interview checklist. Structural changes require a plain checker invocation after the last observed change. General closeout must avoid the development batch recipe and unnecessary Git comparisons. The register case must preserve payment operation identity while completing the independent rename and typo; its typo-only control must avoid unnecessary context reads and upkeep.

C06 must preserve the original two-owner completed capture, expose conflicting source bytes, block the descendant from updating active owners, preserve scope boundaries, process independent items, and distinguish limited withdrawal from whole-source stop-use and deletion. The CLI public state, actual readback text, before/after files and event snapshots supply mechanical evidence. The coordinator also reads command ordering, saved prose and final responses. Event snapshots cannot rule out every write undone inside a single tool call, and markers alone cannot prove correct interpretation.

## Whole-task observations

In the source candidate, `targets` for method r2 is a separate command. Its ancestor-conflict error is observed before any dependent owner write; the turn leaves both research and creative owners byte-identical. The unrelated personal experience is retained, routine material receives a considered no-update outcome, scope mismatch is rejected, limited experience withdrawal is reconciled, and whole-source withdrawal lists known impacts without deleting originals. A success receipt does not claim that all copies or provider history were covered.

The register fixture supplies both protected context and executable payment behavior. Actual tool traces show the relevant register/owner and implementation were read. Passing it cannot identify which one caused protection, or prove that all large registers are cheap to read. No selective-reading policy was changed. One conflict attempt used unavailable `python`, observed the error, then successfully used `python3`; this execution cost remains in the result rather than being discarded.

The final continuation candidate completes all four phases with preserved source bytes and accepted meaning, scoped creative correction, no context edits or reads in the typo phase, and an actionable interview checklist. Its final checklist asks for supporting and contrary evidence, avoids leading causal assumptions about light/sleep, restricts creative material to non-identifying atmosphere and leaves canon changes under their separate authority. It runs the plain checker after observed structural changes and never loads the development batch recipe. The baseline also produces correct content, but loads the development recipe and its phase-2 `--since HEAD` comparison returns INCOMPLETE; that is insufficient for the required structural check.

The final paired continuation sums are **169.425 seconds / 547,392 input-plus-output tokens for baseline**, and **192.490 seconds / 929,863 tokens for candidate**. These are total native turn usage, including cached input, not provider billing or experiment wall time. Candidate phase 1 uses the optional source CLI and smaller separate tool calls (24 tool items / 57,290 output bytes versus 18 / 54,731); phase 2 resumes that source state (17 / 61,854 versus 19 / 41,647), while the baseline uses direct owner maintenance. Those different execution choices are observed, not an isolated causal explanation of the cost difference. The earlier candidates were cheaper but failed a criterion or had the ambiguous fixture. No attempt is discarded to claim savings.

The coordinator accepts this bounded correctness/observability repair because the wrong-route and write-after-rejection failures are concrete. This is not user acceptance of higher costs, nor evidence that this execution style is optimal. The source CLI remains optional for simple recording; no new always-on tracking or reading policy is introduced. An efficiency claim would require isolating policy and task-path choices in a representative corpus. No performance improvement or longitudinal usefulness is claimed from these samples.

## Reproduction and scope

Use the [trial guide](README.md) to prepare `--continuation`, `--large-register conflict`, `--large-register typo`, or C06 with explicitly authorized model choice. Preparation performs no model call; native execution requires a fresh output directory and validates the frozen manifests. To compare installed variants, prepare both through the same harness and compare source/fixture identities before running. Do not overwrite failed attempts. The v3 fixture ambiguity and superseded oracles are evidence about the trial method as well as the product.

The matched source candidate changes both the source handoff sentence and the unrelated general checker entry; only the former directly controls the observed failed-target/write boundary. The evidence establishes the observed path, not a statistically isolated causal effect or universal reliability. The final installed candidate source manifest matches every current `skills/`, installer and VERSION byte. The register controls precede the later conditional general/source reference edits; actual control commands read neither changed reference, and their format-4 model and protection owners are unchanged. General/dev format numbers, permission owners, installer replacement semantics and model policy are unchanged. No fresh power-loss, provider collection, arbitrary-entry discovery or months-long production test is claimed.
