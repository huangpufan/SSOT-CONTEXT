# 本仓库怎样用较少的上下文维护公开文档

2026-11-20，项目负责人选用 SSOT-CONTEXT 本仓库做第一次真实试点。资料范围已知时，交付者把获准的现有文档交给维护者，并指出可改的文档。只改一条已定规则就原地改、读回；多个决定一起变更时，先核对各自的负责人和生效条件。交付的是能供下一人使用的文档。宿主负责限制实际可读范围。这个做法已接入本仓库的维护入口，试点时的消费者发行版为 5.13。[项目指令](../AGENTS.md#repo-boundaries) · [阶段状态](context-evolution-route.md) · [逐次回执与判定](../tests/benchmark/results/scoped-maintenance-pilot.json)

## 一份修改为什么需要分两种处理

我们恢复了展馆第四次换班前的 12 个文件，逐文件核对了它们与先前存档的哈希。一道题只要求新负责人更新内部版式，另一道还要求依据两份独立观察更新研究建议。每次写完，新的普通读者只收到实际落盘的手册和必要的研究交接，要做出内外两版成稿，还要说出旧版式是谁选的、当时为什么选它。

普通文档、5.13、此前的轻量候选各做两条交接。六位维护者中五位打开了不在本次授权内的原件。普通文档的单条修改避开了原件，但接手者已找不回旧版式的作者和理由。上次在费表上节省 75.4% 输入的轻量候选，此次在单条版式任务上也出现了历史顺序颠倒。这个结果排除了“只要是一份文件就可以轻做”的判断。

当负责人预先交付允许读取的材料，且交代替换时保留唯一旧理由，新的两条链都让下游交对了当期成稿，也找回了作者和理由。多文档维护者仍然超时：它在两份文档写好前后还向运行记录寻找旁证。保留超时和当时的落盘成果；另起同条件试验，明确只使用收到的材料、必要证据缺失时指出具体缺口、核对后交接。这次维护者在同一时限内完成，下游也交对了。

随后换成温室的开放批次和观测资料。两位读者都找回了旧理由，多文档那一位却在公众稿中用项目符号解释“公众稿应写成段落”。要求对照实际成稿再交付后，公众稿恢复段落，仍有一份工作人员稿把两个展区的事实分别标成“之前”和“之后”，原手册没有给出这层时间关系。需要可以直接使用的成品时，验收者仍须看成品的形式、事实和受众。四次独立的文件授权试验覆盖了只准原文、只准摘要、两者都准和两者都撤回；交付的事实符合授权，范围外原件保持关闭。“两者都准”的答复另有一句把采访误称为唯一来源。试验没有模拟会话中途撤权。[题目、保存点与分项结果](../tests/benchmark/results/scoped-maintenance-pilot.json)

## 两个实际维护事项

第一个事项是 README 把链接的访问约定写得像工具已经强制执行。第一位维护者核读已发表的证据；第二位在新会话中拿到第一位的原始发现，修改中英文介绍。第二个事项是 benchmark 指南的读者找不到已经完成的两次相关试验。第三位维护者从前一笔修改已经发表的版本开始，把指南链接到真实报告。试点和普通检出的对照使用相同问题和原生模型，实际交付者事先选定。第二步的两组编辑都使用同一份实际交接，因而不能把两条查询链当作完全独立的重复。两笔成稿均经过主维护者的文字精简。指南的普通检出还因运行 Python 测试留下了 16 个字节码缓存文件；试点只改了指定指南。缓存没有进入发布。[README 修改](https://github.com/huangpufan/SSOT-CONTEXT/commit/25cb111) · [指南修改](https://github.com/huangpufan/SSOT-CONTEXT/commit/1bdd614)

| 实际任务 | 原有完整检出，输入 token | 试点交付者，输入 token |
|---|---:|---:|
| 核查两种语言的权限说法 | 877,011 | 188,883 |
| 按核查结果修改两份 README | 159,606 | 77,222 |
| 给 benchmark 维护者补齐证据入口 | 731,533 | 244,635 |
| 合计 | 1,768,150 | 510,740 |

三次执行合计少 1,257,410 输入（71.1%），工具调用从 78 次减到 35 次，各次运行时间之和从 432 秒减到 291 秒。对照维护者有完整的已跟踪公开文件和原有指令；试点还改变了收到的文件范围，因此不能把差额全算在某句话上。原生输入核实了新指令确实被加载。在实际交付版本的独立 Git 检出上，撤下试点段落，项目指令逐字恢复到先前版本，两份已修 README 的哈希不变。恢复试点后检出干净。[采用提交](https://github.com/huangpufan/SSOT-CONTEXT/commit/890c957) · [回退读回](../tests/benchmark/results/scoped-maintenance-pilot.json)

## 下一位维护者遇到了什么

指南发布以后，照它前往早期研究的读者会在最后一段看到“下一项可验证的改动”，但这项试验已经做过。另一位维护者从实际发布的新版指南接手，给历史报告加了带日期的结果入口，保留当时的判断。此时交付范围直接取自两组共同收到的任务中写明的三个文件。普通检出输入 1,160,963，试点输入 129,968。两边都给出了可用证据，主维护者把试点稿压缩为一段并核对链接后发布。加上这次，三个真实事项共四个执行环节，普通检出 2,929,113，试点 640,708，少 2,288,405 输入。四次的执行时间之和分别为 695 秒和 365 秒，工具调用 111 和 46 次。这些时间没有计入主维护者的工作。[后续真实修订](https://github.com/huangpufan/SSOT-CONTEXT/commit/e6ecc50)

## 总账还差什么

到第三项修订推送并读回，共 36 个被试会话，33 个正常完成，3 次超时均保留回执。含研究和对照，输入 7,912,700，其中 7,084,800 命中缓存，另有 464,837 输出。协调者从收到本轮目标到该次交付一共有 77 个原生计量步骤。下面按实际操作回溯归类，每步只算一次。输入含缓存，不表示账单金额。

| 协调者做了什么 | 步骤 | 输入 token |
|---|---:|---:|
| 选定试点、准备和启用仓库指令、读回启用结果、演练回退 | 7 | 1,340,984 |
| 派发、接手、整合成稿、发布及确认；包括两边共用的操作 | 12 | 2,624,277 |
| 选题选材、比对成稿、查验和处理门禁；同一步也服务于研究 | 21 | 4,392,497 |
| 其余研究、测量和报告 | 37 | 7,228,719 |
| 整个窗口 | 77 | 15,586,477 |

扣掉能明确归入试点启用的 1,340,984，四个执行环节省下的输入只余 **947,421** 可抵其他增量。要在这三项维护上回本，试点额外的选材、审稿及返工比普通方式多用的输入须低于这条线。普通对照的成稿没有经历独立发布，无法从共用操作中还原两边各自的调度花费。标题请求缺用量，人的分钟数也未单独测得。研发支出与日常使用分开记。

其中一次发布被完整的提交编号拦下。原提示只给文件名，维护者接着查门禁和正则。现在同一输入第一次就指出第 17 行及“公开提交链接应缩写”，本机路径和消费项目名分开报告，原值不回显。还没有后续真人或模型处理同类问题的耗时对照。

## 用户常问的进度能否直接答

试点前约一周，16 个由用户启动的本仓库顶层会话中，15 个留有用户消息。逐条核对这 48 条消息后，21 条主要在要求调查、设计、实现或部署，17 条是协调、确认、接续或纠偏，6 条直接问方向、范围、原因或进度，4 条属于一次无关的模型查询。没有一条只要求修改一篇点名的公开文档。一次请求可能包含许多文件工作；这组数只能衡量用户实际怎么提问。

这 6 次追问能找回原生调用记录。5 次正常结束，合计 15 次模型回复步骤、10 次工具调用、4,099,055 输入，其中 4,072,960 命中缓存。第 6 次正是异常终止前要求简单讲清因果的提问；没有答复和返回用量。这是试点前用户在长对话中实际经历的成本。相同的短问题，在已有很长上下文的会话里也可能很贵；含缓存输入与实际费用仍须分开看。

三项修订发布后，用负责人实际反复问的进度问题，让新人从同一完整公开检出接手作答。两边都没有预先挑文件，只有加载的项目指令不同。普通方式用 677,732 输入、29 次工具调用、213 秒，试点用 197,745、16 次、140 秒。两人都找到了四个阶段已完成、执行者节省与总收益待定的区别。两篇中文答复却分别有 2,697 和 2,814 个字符，仍需精简；试点还把早期单条规则的结论写得过宽。这个问题暴露了日常查进度的摩擦，单次执行差额不能抵作整个项目的长期收益。

随后把阶段结论提到路线页开头，分别试了两种项目指令。同题第一种用 169,762 输入，答了 1,715 个字符；另一种要求只转述开头，反而用了 262,187 输入、答了 2,372 个字符。问具体缓存数量时，接手者能沿链接正确找出 16 个且均未发布，但引用了临时检出路径。两种指令都没有稳定交付可直接转发的短答，均未加入仓库常驻指令。保留路线页开头四句话，读者可以直接取用。重复同题和细节反例只计入研究成本。
