# 换了负责人、方法或文档，项目怎样接着做

一个展馆把内部简报交给新编辑。交接前，新编辑已提过改用表格。交接后，她才有权决定内部版式，并正式采用了表格。合作方仍要散文。同期，研究组要判断能否扩大试验，两份先后抵达的报告一开始来自同一次观察。下一班需要写出两份能用的简报，还要给出正确的研究建议。能背出历次会议的结论，只解决了其中一部分问题。

5.13 把旧偏好仅存的依据留在获准维护的位置，修订了决策权交接的说明，给已完成的来源记录增加了与当前文档的字节比较，也让子目录里的空间入口可以核对平级目录下获准访问的指南。研究、软件和创作继续使用各自的证据与文档。下面的分析与案例供维护者判断共享协议应该改到哪里。消费者沿用原入口。

## 把一个条件改掉，正确行动会不会变

长期 context 要支持的最小判断是，某个人在某个时间接手这项工作，在现有权限和证据下，下一步可以做什么，还有什么值得为以后保留。这里把“向量”用作构造反例的方法。每一行都能单独换一个条件，让同一句话或同一份文件产生不同后果。裁决权、决定已获接受、实施已完成可以分别变化。它们需要一起求出当前做法，不能用一个“有效”字段替代。

| 可分别改变的条件 | 保持其他条件，哪两种情况会改变判断 | 谁负责，本轮怎么看 |
| --- | --- | --- |
| 目标及结束条件 | 已做完一轮试验；约定的目标可能是交付这轮结果，也可能是取得两份独立证据 | 长期目标归主题文档，短期目标归任务。已有 5.11 的停止与接续路径，本轮用真实研究回执检验两例门槛。 |
| 同时追求的目标及资源 | 两项收藏各需一台次，两台设备可能都可用，也可能有一台次已兑现给另一项借展 | 可用资源由排期维护者说明，取舍由约定的裁决者负责。分别检验充足、冲突、已预订、已释放。 |
| 材料的用途与地位 | “我想用表格”可能是建议、个人偏好，或负责人已接受的办法 | 保留原话、它回答的问题及适用范围。六班交接中同一个人先提议、后获任并采纳。 |
| 人、权限与授权期限 | 相同签字发生在委托期内或期满后。今天签字人都已卸任 | 保留当时谁能改这项选择、谁实际决定。项目授权可以转移，已作决定是否终止由该决定的约定裁决。 |
| 适用对象与用途 | 同一条消息供内部或合作方阅读，原话也可能获准纪念性保留、未获准公开使用 | 受众指南与资料持有人分别负责。试验核对内部和合作方实际成稿，撤回使用的旧测试继续覆盖来源侧。 |
| 方法、前提与判别能力 | 两份观察都通过，其中一份可能是正常冷交接，也可能是用来校准裁判的参考组 | 研究方法归项目研究文档。软件用运行证据，创作用约定的读者体验与正典，定量方法留在适用的项目。 |
| 证据身份、独立性与覆盖 | 第二份报告可能重述原会话、来自另一个项目样本，或缺少辨别两者的依据 | 可追溯到同一事件的多个视图只提供一次该事件。试验分别给出相同、不同、不明的来源，也实际修正了一道证据不足的题。 |
| 决策、执行及已发生的效果 | 可以批准改方法、执行新方法，或者只是负责写汇报；外部动作的回执也可能晚到 | 决定归决策文档，执行与重试归任务宿主。5.11、5.12 有停止、迟到和送印证据，本轮只执行本地任务。 |
| 过去的进展与今天的材料 | 昨日完成了读回。今日同一位置的指南可能完全相同，也可能改了方法还保留来源标记 | 来源任务保留完成记录，状态查询在允许读取时比较该次回执与当前绑定。正文作者判断改动是否影响结论。 |
| 发现路径及位置 | 目标和方法没有变化，指南标题被改名，或其维护位置在入口的平级目录 | 入口负责把读者送到现行解释。普通链接、单选入口和显式选择的多段路径有不同的检查范围。 |
| 读取、留存、改写和发布的权限 | 同样一份历史回执，可以允许读取当前正文，也可以只准盘点既有登记 | 由持有人决定。实测逐个监听来源和指南的打开事件。任何一次查询都不应替持有人解除限制。 |
| 捕获、找回与维护的代价 | 新会话可以直接从操作指南读懂生效条件，也可能要翻多期会议记录才能还原 | 入口保持短小，原因留在主题或历史文档。比较有技能和纯文档的整个交接，并记录失败、读写和推理成本。 |

例如，“优先做地图”在有两台次时可以表达偏好。在只剩一台次时，照做就会让另一项已接受的目标逾期。此时先看谁有权承担这个代价。如果董事会保留裁决，可以先提交两种有条件的安排和无需台次的搬运清单。如果董事会已委托值班人员判断，则可以作出选择、说明理由，把另一个目标仍面临的延迟交接下去。给所有项目增加同一种优先级评分，会抹去这项区别。

从生命周期逐步回看，Bootstrap 要让新人能从入口找到目标及其维护者。Preflight 核对当前任务依赖的范围与证据。Closeout 把已接受的更改落到原维护位置，暂停时把实际进展交给任务记录。Doctor 能核对明确选定的文件及来源状态。Audit 和 Skill 两个兼容入口交给上述责任方处理。接受、撤回、读回和文档在场是不同事件。这些关系适用于分析；至于哪些维度值得在一个项目中写下来，取决于它们能否改变下一次决策。上表覆盖的是这次提出的问题。跨月遗漏率、隐藏来源和其他领域的全部需要，仍无法从这组试验证明。

三个本地消费项目的现行入口展示了这种差别。桌面软件将用户可见的验收、运行时职责和发布记录分别交给产品、架构和流程文档。研究型助手把研究主张交给活论文，把运行中的事项和后续验收交给任务系统。长篇创作空间则把已接受的设定、可选素材和当前可写范围分开。一个入口应当把“下一步凭什么做”带到正确的位置。给三类项目统一增加进度百分比，既无法说明软件是否已在目标环境运行，也无法说明一段试写是否已被作者接受。此次只读取这些入口并核对安装文件，项目自身的内容和工作流均未变更。

## 实际改了什么

**决策由谁接续。** 5.12 的决策历史要求修改者取得原决定者本人的同意，收尾又要求明确的用户决定。项目可能已明确把某个范围交给新负责人，两句话在这种情况下会给出不同指示。现在按项目的决策流程查有权接受该项变更的人与适用范围，保留早先选择和后续替代的实际归属。只接手执行、只有职位、只提出改动的人，均须依现有授权判断。涉及受保护结果时仍须有针对具体损失的接受依据。英中文决策模板同步提示交接来源。[决策证据](../skills/ssot-preflight/references/memory-model.md#human-decision-evidence) · [决策历史](../skills/ssot-preflight/references/memory-layout.md#decisions)

**改写指南时，旧理由存在哪里。** 第一次六班试验里，5.12 和第一版候选都曾把 Cora 的原话写进指南。第四班依据签字纪要更新指南时，两组都丢了“方便工作人员扫读”的理由。当前简报仍然完全可用。新开会话追问来由，两组都据实回答现有记录无法确定。问题出在日常替换路径只明确要求在历史决策文档里保留缘由，有的项目只在现行指南里存了这一份。发布版在改写前查旧依据的位置。有获准使用的独立来源就保留可用路径，唯一依据在当前段落时保留必要的原话、归属与理由，并交代哪一部分何时被取代。出处本来缺失、或当事人已撤回保留许可，都有相应处理。[变更对账](../skills/ssot-preflight/references/context-tiering.md#reconcile-changed-guidance)

**读回之后，现有文件改过吗。** 在 5.12 的真实 CLI 中，先读回研究指南并完成来源任务，修改方法文字而保留标记，再次查询，完整的状态报告与改动前逐项相同。5.13 的 `completion_check` 以完成时的回执为基准。完成以后即使又读回了别的版本，也不会挪动旧基准。正文相同时返回 `same-bytes`，有改动时返回 `different-bytes`，正文可读时还能看到该来源标记有几个。修正无关章节也会使字节不同。对决定含义的影响要读相应段落才知道。绑定已搬走、文件不可用、仅获准读元数据、缺少旧摘要的情况分别显示。历史完成状态仍然可查。[来源状态和回执](../skills/ssot-doctor/references/source-integration.md#readback-progress-and-recovery)

**让现有文档留在原处。** 有些空间把入口放在 `context/`，编辑指南在平级的 `editor/`，二者属于同一约定项目。5.12 能提示这是外部路径，却无法核对该标题。5.13 允许在检查时指定已商定的空间根目录，并列出获准打开的文件。下面的命令从项目根目录运行，能对这两个文件的链接和标题给出结果。没有选中的来源和 Git 历史继续按原授权处理。[选定文件的检查](../skills/ssot-preflight/references/source-retention.md#selected-mechanical-checks)

```bash
python3 .agents/skills/ssot-doctor/assets/scripts/ssot-check.py context/entry.md \
  --space-root . --owners ../editor/guide.md
```

## 两位讨论者改变了哪些设计决定

两位讨论者先读同一个冻结的 5.12 快照，各自提出反例，再在原会话里接受质询。Antigravity 三轮请求的配置均为 `gemini-4-neon-xhigh`，服务端返回型号为 `gemini-4-neon`。Claude Code 三轮返回 `claude-opus-5-5`。两者均只参与设计讨论。实际行为试验由 GPT-6.1 Terra 执行。

Claude Code 首轮认为，应先找长期使用失败，再考虑给记录加标准字段。质询后它撤回了四个固定字段和新建常驻失效账本的建议。我们采纳了它关于授权到期、已占用资源和旧回执缺失的反例。对“先冻结所有改动数月”的建议，当前工具已经能稳定复现两处差异，足以当轮修因。长周期成本仍待真实使用观察。

Neon 指出嵌套入口与平级指南的问题，也提醒同一指南可能只改了无关章节。它在第二轮认可受限检查默认排除 Git 历史。我们采用了显式空间根目录、只选获准文档和纯文档长链对照。未采用默认遍历所有后代、从历史推断权限或给每个消费者加一张覆盖表的建议。这些选择会改变检查的读取范围。已有协议把权限和保护决定留给项目，在正文层面处理这两件事更合适。

第三轮把这次实际丢失旧理由的轨迹交给两位讨论者。Claude Code 指出新负责人的决定可能只替代旧偏好的部分范围。Neon 提醒原话全都堆进现行指南会让退役选择再次被照用。最终把修改放在替代动作里，保留现有来源时用定位线索，只在必要且获准时保留唯一依据。普通文案替换另设对照。

| 真实项目跨月重启 | 软件项目能否定位旧验收依据，研究项目能否区分方法变更前后的结果，创作项目能否找回某个取舍而不误用退役设定 | 经项目持有人同意，从自然发生的变更开始，保留当时的入口、原话许可与下一次真实任务。记录找回失败、误用、查找成本和人的补救。有跨领域复现再考虑共享规则。 |
| 两个维护者同时改有关联的约定 | 后合入的局部调整会不会覆盖另一位维护者刚接受的例外，接手人最终照哪个版本做 | 本轮按顺序交接。先冻结具有相同终态文件名、不同接受顺序的对照，再看改写责任在共享协议、版本管理还是项目裁决流程。 |
| 长期积累后的读取成本 | 面对二十次部分替换，读者能否迅速找出现行条款、追回应保留的理由，并跳过已撤回的材料 | 让相同任务分别使用现有指南、独立历史来源与纯项目文档，记录错误选择、无法找回、实际读取和人工介入。简化方案只有在保护这些结果的前提下才值得替换现行路径。 |

这些观察支持不同的项目继续使用自己的尺度。软件项目的运行验收、研究项目的独立样本、创作项目已接受的正文，各自产生能回答该项目问题的证据。共享协议维护的是谁能改变这个目标、方法或选择，变化何时生效，以及下一位接手者去哪里确认。
