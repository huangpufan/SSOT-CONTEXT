# 5.16 怎样在不削弱权限与回读前提下减少 API 往返

**2026-11-24，经过两阶段共 16 组干净配对的 Codex 对照试验后，发布协议 5.16。** 前两项对照（[混合任务](2026-11-24-mixed-edit-study.md)与[热读文档拆分](2026-11-24-hotpath-split-study.md)）证明，在 Codex 这类高前缀宿主上，单次 API 往返约携带 18k–20k 输入 token；放宽触发词会诱发回退，拆出 3 KB 参考文本的收益又远小于单次往返方差。5.16 转而消除协议表述本身造成的可避免串行往返：允许在**打开任何链接文档或受限来源之前**，将所选技能 `SKILL.md` 与入口文件头/标题放在同一步读取；核实入口权限和保护规则后，合批执行彼此独立的已授权读取；保存单条修订后，允许在同一工具步骤紧接着从磁盘重读落盘正文完成回读，并合入此前定位的 `stop here,` 与 `Otherwise,` 守卫。

在 Codex CLI `0.171.0`（`gpt-6.1-terra`，`medium`）上，全部 16 组干净配对（12 组主矩阵 + 4 组未见过的独立确认任务，外加 4 位冷接手读者）**零质量或安全回归**；合计总输入从 **1,832,077** 降至 **1,562,792（-269,285，-14.70%）**，API 往返从 **94 次**降至 **80 次（-14 次，-14.89%；10 组更少、6 组持平、0 组变多）**，输出从 15,902 降至 13,801（-13.21%），工具返回字节从 400,470 降至 387,461（-3.25%）。[逐次原生回执、候选补丁、内核打开见证与冷读者记录](../tests/benchmark/results/batching-readback-5.16.json)

## 5.16 改了什么，以及未改什么

本次变更共涉及 8 处文件（`VERSION`、`skills/ssot-preflight/SKILL.md`、`skills/ssot-closeout/SKILL.md`、`skills/ssot-closeout/references/decision-capture.md` 与 `en`/`zh` 双语 `adapter-thin.md`、`context-adapter.md`），**零新增文件、零预算扩容、零触发词放宽、零规则删减**：

1. **技能与入口同一步读取，严格早于任何链接来源。** 5.15 在适配器写的是 `starts with $ssot-preflight before opening the entry`，模型在 5.15 下经常把 `cat SKILL.md` 和 `cat SSOT/README.md` 拆成两轮串行往返。5.16 明确允许在同一步读取所选 `SKILL.md` 与入口文件头/标题，但必须在打开任何链接的 owner 或受限来源之前完成权限与保护核验。
2. **核验权限后合批读取。** `ssot-closeout/SKILL.md` 明确在核实入口的格式、权限与保护规则之后，彼此独立的已授权读取可以合批执行，复用已有段落。
3. **保存后同步骤落盘回读。** `ssot-closeout/SKILL.md` 与 `decision-capture.md` 明确写后必须**从磁盘**重新打开已保存正文，但允许在同一工具步骤写入之后紧接着读取磁盘文本，在回复或依赖性工作之前核对真实落盘结果。
4. **单文档改写收尾守卫。** `ssot-closeout/SKILL.md` 补上 `stop here,` 与 `Otherwise,`，防止格式 5 已完成的单文档正文改写误跳入完整的 `context-spaces.md`。

已有 5.15 消费者升级技能后即获得技能正文改进；若要启用适配器中「技能与入口同一步读取」的提示，刷新仓库里 `SSOT-CONTEXT:BEGIN/END` 受管指令块并重启 Agent 即可，上下文文档格式（4 与 5）均保持不变。

## 协议变更四问与证据边界

1. **是否属于通用协议？** 是。权限前置下的技能/入口合批、已授权独立读取合批与写后同步骤落盘回读，对开发仓库（格式 4）和通用空间（格式 5）普遍成立，不绑定特定项目或业务领域。
2. **替代了什么？** 用明确区分「权限核验前（仅限技能正文与入口头/标题）」与「权限核验后（合批独立已授权读取）」的顺序约束，替代原先客观上促使模型串行多走 1–2 轮的模糊先后表述；同时在 `ssot-closeout/SKILL.md` 补上 `stop here,` 与 `Otherwise,` 守卫。不增加新文件，不放宽任何现有预算上限。
3. **验证层级是否匹配影响？** 全部 16 组配对在官方安装器接线、隔离 `bwrap` 沙箱与真实 Codex 会话中运行，覆盖格式 4/5、中英文适配器、双轮热刷新、失效路由、无关错字零触发、冷接手读者、全部写入落盘回读校验以及经正负对照校准的内核 `inotify` 文件打开见证；所有离线门禁测试全部通过。
4. **整项任务净效应与局限是什么？** 在 16 组配对中，总输入降 14.70%（-269,285），API 往返降 14.89%（94 → 80，无一例退化），输出降 13.21%，工具返回字节降 3.25%；无关错字任务几乎完全持平（+40 token / +0.09%，零协议文件读取）。需要诚实说明两项非同步指标：
   - **未缓存输入微升 5.49%（196,237 → 207,016）**：逐请求排查显示，工具返回总字节实际减少 3.25%，增幅主要来自服务端前缀缓存抖动（仅 `parcel_warm_r1_candidate` 第 1 次请求缓存命中 7,040 而非常态 12,288 就单独贡献 +5,288 未缓存输入）及适配器增词约 +7–19 token。
   - **总挂钟时间增加 61.0 秒（719.3s → 780.2s，+8.48%）**：由单次上游响应长尾（`dev4_undoc_rule_r1_candidate` 4 次往返耗时 150.2 秒 vs 基线 40.8 秒，尽管其输入少 22,520 token）主导；不将该数字解释为稳定耗时回归，也不宣称稳定加速。

两阶段合计 37 个完成会话（33 个执行者共 35 轮 + 4 个冷读者）及 1 个超时尝试，总计消耗 3,607,940 输入（缓存 3,169,024、未缓存 438,916）、31,245 输出、187 次 API 往返、148 次工具调用、含超时共 1,829.2 秒。完整两阶段冻结现场与原生日志（剔除 `codex-home`、`probes` 与凭据文件）保存在本机私有归档 `batching-v5.16-b8d6577-20261124.tar.gz`，SHA-256 记于[结果文件](../tests/benchmark/results/batching-readback-5.16.json)。本证据仅覆盖 Codex CLI `0.171.0` + `gpt-6.1-terra`（`medium`）与每题 1–2 次重复，不能直接外推至不支持合批工具调用的宿主或真实线上任务分布。
