# 协议 5.17：超长不变量表的可选主题分片与跨分片保护校验

**2026-11-24，在 8 组冻结配对 Codex 试验（16 次 `gpt-6.1-terra` `medium` 原生会话）全部满足预声明采纳门禁后，发布协议 `5.17`。** 此前 [Stage 5 真实会话审计](2026-11-24-real-session-stage5-audit.md)发现成熟开发仓库的 `SSOT/README.md` 会因 360+ 条不变量膨胀至 251 KB，15 天内触发 1,351 次入口截断。`5.17` 保持 `ssot_format: 4` 与 `ssot_format: 5` 完全向后兼容，不增加常驻适配器或技能目录字节数，仅新增“可选主题分片”协议规则（+133 词）与 `ssot-check.py` 跨分片机械保护校验（+18 项单测）。

## 协议变更四问（`CONTRIBUTING.md`）

1. **这属于通用协议职责吗？** 属于。成熟消费仓库随时间必然积累上百条产品承诺与架构不变量；现行协议允许入口按节读取，但把全部不变量行固定压在单文件 `SSOT/README.md` 内，并由 `ssot-check.py` 仅对单文件执行 ID 唯一性与已确认规则历史比对，使消费仓库即使想拆分也缺乏受保护的统一方式。单仓本地改法无法提供跨分片防篡改检查，也不能让新会话稳定按主题按需读取。
2. **它替代或新增了什么？** 不替代也不废弃单文件内联不变量表，不提高任何 CI 预算上限，也不触碰适配器受管块或技能发现目录（均 +0 字节）。仅在 4 处协议文本新增 133 词：[`memory-model.md §5`](../skills/ssot-preflight/references/memory-model.md#5-invariants) 定义可选主题分片（`SSOT/invariants/<topic>.md` 或带 `ssot_register: shard` 前置元数据的文件，在 `## Invariants` 下用项目列表写明各分片主题范围）；[`ssot-preflight/SKILL.md`](../skills/ssot-preflight/SKILL.md) 说明有分片时读入口跨模块规则加相关主题分片（术语不清或涉跨模块依赖时扩大到关联分片）；[`memory-layout.md`](../skills/ssot-preflight/references/memory-layout.md) 标明可选 `invariants/` 目录；[`batch-closeout.md`](../skills/ssot-closeout/references/batch-closeout.md) 说明收尾写入时按主题落入对应分片。[`ssot-check.py`](../skills/ssot-doctor/assets/scripts/ssot-check.py) 同步增加跨入口与分片的 6 列表格校验、全局 ID 唯一性、相对路径解释锚点检查、孤儿分片报错、跨提交搬迁与删改的 `confirmed` 规则历史比对，以及 `--owners` 受限模式不打开未选分片的隔离保证（且保持大表不发 `WARN`，继续遵守 `test_large_register_is_not_a_warning`）。
3. **验证层级是否匹配影响范围？** 是。验证覆盖两层：机械层 159/159 项 `test-ssot-check.py`（141 项原有 + 18 项新增分片单测，含跨分片重复 ID、分片内非法状态/断锚点、孤儿分片、跨提交无损搬迁通过、搬迁时偷改规则报错、取消链接/删除/替换为越界软链仍报已确认规则被删、格式 5 空间支持及 `--owners` 不可读未选分片零打开）与 65/65 项 `test-bundle-shape.sh` 预算门禁；真实执行层在 Linux 原生 `codex-cli 0.171.0` 上以 `gpt-6.1-terra`（`medium`）运行 8 组反向平衡冻结配对（16 次独立会话），覆盖 360 条不变量的大仓库编码、单主题保护拒绝、跨主题依赖放宽保护拒绝、收尾新增分片规则加 `ssot-check.py` 验收，以及 2 组逐字节一致的小仓库未分片对照组。
4. **整任务净收益与代价是什么？** 在 6 组 360 行大仓库配对中，全部质量与安全 6/6 通过，入口首次读取截断从 **6/6（100%，单次 12,027–45,042 token）降至 0/6（0%）**，全部工具调用总截断从 **13 次降至 4 次（-69.2%）**，聚合原生输入下降 **21.60%**（1,178,239 → 923,693，且 6/6 组各自全部下降，幅度 -10.43% 至 -48.38%），未命中缓存输入下降 **16.92%**（166,143 → 138,029），API 往返从 37 降至 34（-8.11%）。在 2 组未分片小仓库对照组中，质量与安全 2/2 通过且无回归（原生输入 -5.95%，未命中缓存 -20.19%，往返 13 → 12，截断 0 → 0）。代价为运行时协议净增 133 词（18,622 / 18,700 词）、检查器脚本净增 6,349 字节（60,611 / 65,536 字节）；消费者是否分片完全自愿，无需格式升级或强制迁移。

## 试验设计与冻结采纳规则

基线为 `5.16`（提交 `3c63732`），候选为未提高预算上限的 `5.17` 冻结拷贝。大仓库组（Group A，6 组配对）按真实生产空间的结构构建 360 条不变量（30 条跨模块通用规则 + 9 个主题各 36–37 条 = 330 条主题规则，基线与候选的 ID 集合、规则正文、状态与来源完全等价）：基线按 `5.16` 最佳形态全部内联在 `SSOT/README.md` 的可搜索主题标题下（约 165–173 KB），候选保留 30 条跨模块规则在 `SSOT/README.md`（约 13.5–13.8 KB）并将 9 个主题组放入 `SSOT/invariants/<topic>.md`。对照组（Group B，2 组配对）两侧夹具逐字节一致（937 B / 618 B）。全部夹具在调用模型前均通过各自版本的 `ssot-check.py`（0 错误 0 警告）、`codex debug prompt-input` 6/6 技能发现探针与负向 Oracle 校验。

预声明采纳规则要求以下 5 项同时成立才发布 `5.17`：(1) `ssot-check.py` 通过全部 141 项原有 + 至少 15 项新增分片测试；(2) 全部 8 组配对质量与安全 100% 通过；(3) Group A 入口读取截断降为 0 且聚合原生输入下降 ≥20%；(4) Group B 未分片对照 100% 通过且无明显成本或往返回归；(5) `test-bundle-shape.sh` 65/65 通过且零预算扩容。

## 关键行为观察与证据边界

- **跨主题安全扩大有效：** 在 `large_cross_topic_protected` 中，用户只提了账本批量导出（`billing` + `export`）跳过内部调用的 `X-Tenant-Id` 校验，未点名鉴权模块；候选版先读取 `SSOT/README.md` 后主动扩大读取 `invariants/auth.md`、`invariants/billing.md` 与 `invariants/export.md`（跳过其余 6 片无关分片），命中 `AUTH-12` 并零修改拒绝，输入仍低于基线 11.29%。
- **收尾自动落片并同步索引：** 在 `large_add_invariant_closeout` 中，候选版自动将新确认的 `WHK-38` 写入 `SSOT/invariants/webhooks.md`（使用正确相对锚点 `../../docs/webhooks.md#请求签名`）、更新 `SSOT/README.md` 分片索引计数并补充 `docs/webhooks.md` 解释节，运行 `ssot-check.py SSOT --since HEAD` 一次通过，输入节省 29.81% 且 0 截断（基线 3 次截断）。
- **区分入口首读截断与二次合批截断：** 候选版全部 6 组大仓库的首次 `SSOT/README.md` 读取均为 0 截断（基线 6/6 截断，单次 12k–45k token）；候选版残留的 4 次工具输出截断全部来自后续步骤把 `memory-model.md`、多个业务文档与 1–3 片分片合并到同一 `exec_command` 批处理返回，而非入口文档本身截断。
- **范围边界：** 本次实测覆盖单一授权低价模型（`gpt-6.1-terra` `medium`）与单一宿主（Codex CLI `0.171.0`）上的 8 组合成 360 行夹具，未测定 Claude Code 或 DSH 宿主，也未在真实重型仓库完成迁移后的多周自然会话统计；后续在消费仓库自愿分片后仍需以真实会话复核。
