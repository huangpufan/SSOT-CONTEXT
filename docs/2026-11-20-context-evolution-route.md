# 降低 SSOT 使用和维护成本，走到哪了？

**2026-11-24，委托子 Agent 跳过条款的 12 组 Codex 配对试验决定保留协议 5.16，不发布 5.17。** 24/24 会话完成且通过行为核验，但 6 组主委托场景上 5.16 基线本身已 6/6 跳过冗余协议读取（`proto=[]`），候选版反使主组输入升 +7.46%（269,620 → 289,745）、顶层对照升 +25.41%，且在修改格式 5 空间文档的反例上跳过了 `ssot-closeout` 与 `source-retention.md`。这说明 Stage 5 的子 Agent 预检税主要源于消费仓库此前 0/5 同步最新指令块、父级未给清委托边界以及 251 KB 巨型不变量表本身，而非 5.16 缺少跳过条款；下一步优先级转向超长不变量表分片（P2）与已同步 5.16 后的真实观测。[委托子 Agent 对照研究](2026-11-24-delegated-subagent-study.md)

**2026-11-24，完成 Stage 5 真实会话审计（5 个在用空间近 15 天共 386 条纯净消费会话，零收费模型调用），定位出三项合成夹具从未暴露的主瓶颈并落地工程减负。** 实测发现：(1) 5/5 空间的 9 份 `AGENTS.md`/`CLAUDE.md` 指令块均停留在 `5.5` 之前，导致 `5.5`/`5.14`/`5.16` 降本路径零落地；(2) 成熟仓库的 `SSOT/README.md` 达 251 KB / 366 条不变量，15 天触发 1,351 次入口截断与 1,170 次协议截断；(3) 211 个 Codex 子 Agent 线程占全部输入 52.6%，91% 从头重跑 preflight 而仅 12% 改代码子 Agent 写 SSOT；同时证实 `ssot-check.py` 在生产中 20 次拦住未经授权的已确认不变量修改，且旧兼容壳与 `context-source.py` 在 386 会话中真实调用均为 0。本轮先零协议改动落地受管块核验/同步（`install.sh --check-block`/`--sync-block`）、解耦 CI 预算尺并新增常驻目录与指令块硬帽、瘦身 `INSTALL.md` 与双语 `README`；后续 `5.17+` 优先攻关子 Agent 委托路径与超长不变量表分片。[Stage 5 真实会话审计](2026-11-24-real-session-stage5-audit.md)

**2026-11-24，5.16 通过权限安全合批与同步骤落盘回读降低 API 往返与总输入。** 在 16 组 Codex 干净配对（12 组主矩阵 + 4 组未见独立确认，另保留 1 次基线上游超时原记录并完成配对重跑）中，全部质量、冷接手、落盘回读与内核 `inotify` 零越权打开校验通过，总输入从 1,832,077 降至 1,562,792（-14.70%），API 往返从 94 降至 80（-14.89%，10 胜 6 平 0 负），无关错字保持零协议误触发，且零新增文件、零预算扩容。[5.16 合批与落盘回读实测](2026-11-24-batching-readback-v5.16.md)

**2026-11-24，拆分热读参考文档（`memory-model.md` / `context-spaces.md`）的两轮 Codex 对照继续保留 5.15。** 第一轮证明把高频交叉引用的第 3/5 节拆出会让 `dev4_protected` 固定多出 1 轮往返（+14.5k/+18.2k）；第二轮收敛为只拆预检不读的第 2 节与格式 5 搭建/兼容/Doctor 段落，12 组配对（含 Parcel desk 编码与双轮热刷新）24/24 质量与安全全过且零跳读，但 3 KB 体积节省（同轮数省 3k–6.6k）远小于单次 API 往返波动（±17k–34k），总输入持平（1,519,311 → 1,524,740，+0.36%），不值得为此增加文件碎片。[热读拆分实测与往返占比分析](2026-11-24-hotpath-split-study.md)

**2026-11-24，混合任务（单文档改写兼查另一文档）的 Codex 独立对照保留 5.15。** 10 组配对覆盖格式 4/5 与四类安全反例，质量与边界全过，内核 `inotify` 确认撤权原文零打开，但候选版合计输入从 825,285 升至 886,169（+7.4%）。原因在于 5.15 在 Codex 上未出现 Flash 的 243k 失控，且放宽适配器诱使受保护任务先读 Closeout 再回退 Preflight（多出 2 轮往返、+34,559 输入）；第一轮同时发现 `ssot-closeout/SKILL.md` 缺少 `Otherwise` 守卫会误读 `context-spaces.md`。[混合任务实测与机制分析](2026-11-24-mixed-edit-study.md)

**2026-11-21，5.15 降低了 Codex 每次列出技能的输入开销。** 相同的无工具请求做了两轮，每次少用 247 个输入 token。跨文档查询试了两种改法，均有任务变贵，沿用 5.14 的查询流程。[5.15 安装实测](2026-11-21-skill-discovery-cost-v5.15.md)

本仓库采用的单文档查询和修改方式已进入技能包 5.14，开发仓库和通用空间均可使用。已获准的小改直接更新原文档并读回，涉及多个负责人时核对各自的决定，保留后人需要的旧理由。此前本仓库已交付三项真实维护，四个执行环节少用了 228.8 万输入 token。启用和演练用了 134.1 万，计入选材、审稿和返工后的净节省仍未测定。

截至 2026-11-20，四个环节的输入从 292.9 万降到 64.1 万，降幅 78.1%。这是本仓库采用前后的执行者数据。另见[消费者安装 5.14 后的八项同题比较](2026-11-20-scoped-owner-v5.14.md)。目标覆盖日常查、改和交接，也包括人的等待与补救。[长期目标](../DESIGN.md#accepted-direction-reduce-the-cost-and-friction-of-using-and-maintaining-context) · [实测与总账](2026-11-20-scoped-maintenance-pilot.md)

## 接下来怎样决定

优先处理真实生产中高频重复出现的瓶颈，而非继续在合成小文档上微调 1–3 KB 文本拆分。现已通过 `install.sh --check-block` / `--sync-block` 消除指令块漂移并排除了在适配器增设子 Agent 跳过条款的方向；下一轮优先攻关成熟仓库的超长不变量表分片与按主题索引（P2），并在已同步 5.16 的真实空间上复测实际会话分布。试点前一周的 48 条用户消息里，6 条明确问进度、取舍或原因；下一位问进度的人，仍应能直接从本页得到简短答复。已明确负责人和范围的公开文档，可由当前维护者就地处理；需要受限原件时，仍由负责人提供授权材料。

今后评估全流程收益时，将普通文档与这套做法从接单到交付的成本放在一起看，包括选材、返工和等待。若普通文档同样可靠又更省，该类工作就用普通文档。[真实试点记录](2026-11-20-scoped-maintenance-pilot.md)

单条费表、跨班历史和多文档换班怎样影响了以上判断，可查[单条规则对照](2026-11-20-ordered-lookup-cost.md)、[五班交接](2026-11-20-read-trigger-study.md#只凭维护后的文件能交出什么)和[跨领域实测](2026-11-20-context-paths-study.md#发行裁决与整组实测)。[试点前后的选题依据](https://github.com/huangpufan/SSOT-CONTEXT/blob/99e5537/docs/context-evolution-route.md)保留了当时的任务权重与取舍。
