# 补录历史时，怎样既找回决定，也守住撤回

博物馆要重新整理展品目录。登记员已经收回一份访谈的展览使用许可，原件仍由寄存者保存，目录里也留着出处。另一份访谈继续有效。接手者应当从第二份访谈找回陶瓷标签的书写规则，同时让第一份访谈保持关闭。开发项目有一个对应的问题：分支合并以后，下一位维护者还需要知道当时为什么拒绝一个方案；若上次只检查了后半段，也需要知道从哪里接着查。

从这两个交接结果回看 5.8 的六个入口，问题出在 Doctor 选择检查对象和决定补录进度的两处。5.9 修订了这两条路径。首次搭建仍由 Bootstrap 处理，日常读取仍走 Preflight，决定仍保存在原有 owner。两条兼容名称继续转交原来的工作，开发仓库和通用空间分别沿用格式 4 和 5。

## 谁实际打开了原件

把两份访谈作为文本文件，许可表和导出索引分别说明用途与位置。在 5.8 的一次会话中，撤回第一份时只打开了第二份。允许两份时，目录同时保留了第一份的展柜题名和第二份的标签顺序。仅看这两个结果，很容易判断原有协议已经够用。

换一个仍属正常使用的存放方式，结果变了。博物馆把访谈存成 Markdown，空间入口保留可点击的出处，允许读取的索引也链接到原件的标题。5.8 的 Agent 在给用户的答复里说跳过了第一份访谈。它执行的结构检查却报告了原件正文里一张失效插图的文件名。用 Python 的文件打开事件观察同一个 CLI，可以看到全量检查确实打开了原件。事后删掉诊断信息解决不了这次读取。[检查器回归](../tests/test-ssot-check.py)

现在遇到用途受限的通用空间，先从许可记录确定可读文件，再调用下面这样的命令。文件名相对于入口目录。检查器读取入口及指定、直接链接的本地 Markdown 文档，检查这些文件之间的标题和行号引用。间接来源可以依照其权限另行查阅。漏写的文件在本次覆盖范围之外，如果显式指定不存在、未直连或经符号链接改指的文件，检查会报错。报告列出选择范围，末行也标明仅限所选文件。这个模式不核对范围外的链接目标或 Git 历史，获准检查整个空间时仍用原来的全量命令。[使用协议](../skills/ssot-preflight/references/context-spaces.md#mechanical-check)

```bash
python3 path/to/ssot-check.py entry.md --owners catalogue.md permissions.md exports/index.md
```

为什么保留链接？同一份原件可能继续供寄存者使用，当前操作者也可能只有权修改目录和许可表。把所有出处改成纯文本会动到别人的文档，还解决不了已有索引中的标题引用。每次检查按当前用途传入范围，避免为每个空间维护另一份权限名单。旧检查器拒绝新参数时，按许可手工核对并说明缺口。[安装兼容性](../INSTALL.md)

一次早期候选先做了全量检查，再做限定检查；另一次在核对撤回时直接打开了原件。即使最后的目录正确，这两条轨迹都不合格。随后把守卫放到 Doctor 的第一次检查和 Closeout 收到撤回的时刻。撤回时可以核对、清理获准编辑的派生文档，保留下次补录需要的最小来源标识与禁用用途。如果连这个标识也不能保留，就无法指望一个失去临时进度的新会话凭空认出旧材料。交接还暴露过另一类越界：操作者顺手修改了未点名的导出索引。协议因此明确了具名修改范围以及其他问题该报告给谁。

在准备发布的安装包上，撤回者只改了目录和许可表，保留原件、入口和索引，把索引中的旧措辞报告给负责人。把这些文件交给一个没有前一会话和临时进度的新 Agent，它从独立获准的 T24 恢复了“陶瓷标签先列制作者，再列年份，借展也适用”，T17 的题名没有回到目录。检查过两阶段的命令输出、原件字节和文档差异。相邻的全量只读审查获准读取所有材料和历史，准确报出失效插图，工作区未改动。这个对照区分了按用途限制读取与漏检普通链接。

另一轮候选在资料全部获准、任务只要求补录的情况下选择了限定检查。两份访谈都录入，但检查没有核对选择范围外的插图。还有一些候选试图把间接来源传作直接 owner，收到错误后才改用索引。最终指令用“传索引，索引所列的原件另查”说明两者的关系。若任务要求检查整个空间，必须核对实际调用的范围；限定检查的通过结果只能用于列出的文件。

## 合并后，哪段历史真的处理完了

在测试仓库中，展示端保留英文 `Pier`，因为司机的纸质卡上用这个词。登记员同时允许游客地图用 `Berth`。理由和例外只出现在被合并分支的一条空提交里。5.8 的说明沿第一父提交列历史，固定区间内四个提交只能列出两个。旧版 Agent 在这次试验中自行检查了分支，成功恢复了决定。修订针对的是命令和完成条件里的确定性遗漏，这个样本的最终答案在两个版本里都正确。

现在按固定的起止提交，读取结束点可达、起点尚未包含的提交消息，包含合并分支和无文件改动的提交。只对可能包含持久事实的差异深入核对，结合合并结果区分接受的计划、放弃的提议和已经实现的行为。这样增加的是多分支补录所读的消息，不会给普通开发请求增加历史扫描。[Doctor 的 Git 补录步骤](../skills/ssot-doctor/SKILL.md#4-catch-up-on-past-commits)

假设已检查到 A，这次用户只要求处理较晚的 B 之后。B 之后的决定可以立即写入原文档；A 到 B 的空档仍须留给下次。5.8 在措辞明确的对照里保留了 A，在较简短的请求里却主动把起点那条“绿色印刷”决定也录入，并把进度推进至末尾。候选在两个措辞下均保留了 A，同时记录了所请求区间内的码头决定。完整的线性区间与含合并的区间可以正常前进。这里比较了实际文档和保存的提交位置。大型团队仓库的额外读取成本、本地缺对象、多人同时推进同一标记尚未在本轮原生会话中测量。

按 cc 的反例又做了一次纯 Git 检查。两个父提交把同一数值分别改成 40 和 60，合并时才定为 45，并把合并提交的时钟设得早于两个父提交。指定 `--reverse --topo-order` 后，两个父提交都排在合并提交之前。单看非合并补丁找不到 45，而 `git diff M^1 M` 能看到 40 变 45。分段时还须核对已保存位置到目标之间的全部提交都已处理。若原有进度本身记错，可另行取得修正授权；普通补录只前进。这里验证的是 Git 命令，尚未以模型跑这个冲突样本。

## 其余优先级怎样决定

| 使用者的需要 | 已有证据和下一项能改变决定的验证 |
| --- | --- |
| 一项决定已经批准，代码要下个版本才实现 | 5.8 的试验里，Agent 修正了旁边的拼写，同时保留“现行 36 字、已批准 48 字、尚待实施”。没有依据给所有日常 Closeout 再加一次核对。下一步可用实际发生过的回归与明确取消的计划作对照。 |
| 协作者改过工作区，谁有权放宽规则 | 5.8 的只读样本里，登记册有未提交的放宽，负责人原决定与代码仍限制只有登记员能放行。Agent 报告冲突，保留已接受的限制，文件未变。没有覆盖同文件中真实用户已批准修改与未核实草稿交错的情形。 |
| 只读讨论里作出决定，下一会话能看到什么 | 登记员确认了下一季须增加纸张尺寸，同时禁止改文件。5.8 的 Agent 准确转述了决定，说明仓库尚未记录，文件未变。当前 Closeout 已有记录受阻的处理方式。 |
| 小项目搭建投入能否收回来 | Bootstrap 已有针对小范围的审查和冷交接。下一步取一个现成指南齐全、一个藏有重要例外的项目，从搭建跟到三次后继任务，合计重复说明、返工、遗漏、读取和写入，再决定是否继续简化。 |
| 换负责人、跨仓或上下文压缩后仍能找对规则 | 需要能区分“权限真的换了”和“只换了职称”的真实交接，以及父目录会话涉及两个子项目的同题对照。长会话补测压缩后同一决定的例外是否还在。当前样本不足以要求新字段、常驻台账或每次全量重读。 |
| 临时许可到期、同一事实有独立来源 | 优先测试到期前后各一次实际判断，另测撤回单一来源后，仍有独立证据和使用许可的事实能否保留。现有来源可以按用途区分。当前的两份访谈包含不同决定，尚未覆盖同一事实的独立出处。 |

## 本轮如何复核

Neon 与 Claude Code 分别拿到同一个 5.8 仓库快照中的设计、六个入口和上轮报告，先独立排序，再在各自原会话里质询复现和修复方案。Neon 提出的标题引用、符号链接和全量检查的成本进入了设计或对照。Claude Code 提出的只读决定和未提交的规则放宽进入了 5.8 对照。第二轮里，cc 收回了依赖临时连接器状态作为长期依据的建议，提出保留权限 owner、检查合并解决结果和全量检查对照。当前格式 5 的普通 Markdown 链接没有机器可读的 owner 身份，全量对照也确实需要读取允许的原件内部链接，因此选择按调用限定范围。该选项约束检查器，旧工具、任意搜索以及被重新编号的副本仍取决于可见权限和调用方式。若撤回件是某条确认规则的唯一依据，仍由有权负责人裁决规则的命运。这一情形和 DeepSeek Flash 的表现均未实测。Neon 两轮均请求 `gemini-4-neon-xhigh`，回执辨认到 `gemini-4-neon`；cc 两轮回执均为 `claude-opus-5-5`。真实模型回执、逐次工具观察、文件变化及样本局限见[试验记录](../tests/benchmark/results/catchup-5.9.json)。

原生试验共 45 个全新 Terra medium 会话，覆盖 11 个 5.8 基线、30 个迭代候选、4 个与发布文件哈希一致的会话。合计 349 个模型响应，输入 8,255,699 token（其中缓存 7,439,872），输出 65,714。两位设计顾问另计。逐条核对了发布样本的回答、实际命令与工作区差异，并用行为检查器回放失败候选。CLI 的文件打开事件由观察器独立采集；模型进程的判断依据是可见工具轨迹。这批合成任务能展示具体错误与恢复，无法估算自然发生频率、长期维护收益或并发改动下的权限保证。

从仓库根目录运行以下命令。前一项以真实 CLI 检查允许与排除的文件是否打开。后一项默认只准备隔离的安装和资料；在[原生评测环境](../tests/benchmark/README.md#prepare-and-run)里加 `--run-models` 才会实际运行写入者和全新接手者。换成 `--case merge`、`gap`、`bounded`、`linear`、`linked`、`permitted` 或 `full-review` 可分别复验单个场景。输出目录须尚不存在。

```bash
python3 tests/test-ssot-check.py
python3 tests/benchmark/catchup.py --case withdraw-handoff --bundle . --output /var/tmp/ssot-withdraw-trial
```
