# 项目记忆审计与 4.0 改进方案

本次审计关注一个具体问题：项目已经有约束、决定、研究材料和工作记录，SSOT-CONTEXT 怎样让下一位 Agent 找到并维护它们，同时保住用户决定，减少重复文档与重复劳动？审计选择了 Calliope 的项目控制与创作资料维护、核心目标项目 dsh-personal-agent 的用户决定与派工验收，以及 DSH 集合的插件开发和后续验证文档。结论是保留项目既有权威，令 SSOT 成为入口和必要知识的承载处；把对话中刚确认的决定及时写到正确 owner，并在整理和恢复时保住其范围与身份。

这是一次有边界的本地材料审计，不是对这些项目全部文件、用户诉求或运行行为的完整认证。下文用仓库名和仓库内相对路径定位，行号指审计时读到的版本；消费项目未作为本报告附件发布，这些定位不是读者可直接复演的便携证据。报告只摘述工作约束及文档机制，不公开私人作品素材和完整用户对话。本报告是此次研究产物，不建立永久覆盖台账。

## 原始问题与成功标准

问题包括四层：项目事实由谁维护；用户在对话中确认的取舍如何不丢；文件重组时怎样不损失内容；跨会话怎样接回已有任务而不重做。它们相关，但不能全部交给一个文档协议实现。运行时恢复由应用负责，机械登记由项目工具负责，SSOT 负责可靠阅读、知识归属和持久决定。

本次方案的成功标准是：已有领域文件不因接入 SSOT 被迫搬迁或复制；后来的 Agent 能分清用户已接受的选择、尚未接受的建议、已实现行为和观察到的结果；决定在发生时有可追踪且不扩大含义的记录；拆合与迁移能查到重要内容的去向；持续工作沿已有记录恢复；协议及检查器接受同一套 owner 规则。结构检查只能证明格式、链接和注册规则，行为改善需要真实模型任务对照，见[4.0 行为试验](../tests/trials-4.0.md)。

## 真实诉求与协议覆盖

### 现有知识 owner 应继续成立

Calliope 工作边界文档第 92—102 行明确：领域原文维护具体事实，控制页只做站位和入口，skill 的事实入口保留路由；世界设定与正式文本证实的时点分别归属不同工作区。这不是一个等待 SSOT 重建的空白项目。

3.15 的 `memory-model.md` 第 11 行和 `ssot-bootstrap/references/bootstrap.md` 第 33—39 行要求持久事实进入 `SSOT/`、原文变成指针。即使得到迁移授权，也会给已有领域体系增加不必要的移动和维护成本。4.0 纳入仓库内现有 owner：SSOT 入口说明问题与路径，解释可以留在正确的领域文档，只有没有合适 owner 的知识才需要新增承载处。项目内部哪些文件是正式事实、哪些是候选，仍由项目决定；SSOT 不替项目重新分级。

### 用户确认必须及时留下，且不扩大确认范围

Calliope `AGENTS.md` 的“敲定即落盘”与工作边界第 129—139 行要求记录判断、理由、原话、来源与落实情况；近期决策记录实际采用这一组织方式。3.15 preflight 第 4 节、closeout 第 2 和第 4 步已经支持即时保存、来源与部分例外，因此此次不是新增一套决策历史。

4.0 保留并明确即时 capture 的入口：持续规则或重要决定一旦确认，遵循 closeout 写入门禁和 owner 自身写法就更新其 owner，并保存后回读；旧 SSOT 的写禁不阻止项目另行授权的现有 owner 记录流程，用户明确只读仍优先。写入受阻时报告具体缺口、在本会话继续遵守，不声称已经持久化。协议没有授权创建一个暂存决定的额外永久或临时账本。记录用户究竟接受了什么、适用哪个项目或任务，分开未接受的建议、未来行动与当前实现。只有收到的决定才是授权，来源含有一句目标描述不能自动证明接受了所有副作用。用户认可之后，既有授权范围内的落地不再重复询问。

### 管家项目的授权、工程初值与决策体验各有边界

`dsh-personal-agent/docs/LOOP.md` 第 821—840 行提供了直接可用的判断场景。U13 允许系统内部部件解决已有授权范围内的问题，已落实的建子事项只能继承、不能放宽授权；U3 的外部动作预授权仍待决定。因此不能把“内部事务全权推进”压缩成“所有动作都预先授权”。U4 的用户决定是少量并行，具体并发数字属于待真实数据校准的工程初值，不能倒推成用户亲自选定了每个数字。U12 则明确决策优先于进展，用户需要在原地理解并回答；它是产品体验选择，不是 SSOT 协议能替代实现的功能。

4.0 的决定捕获保留问题、答案、范围、来源及局部替换，区分用户接受与工程安排，适用于上述原文。其 owner 路由允许继续以 LOOP 为准，避免在 SSOT 另写一份简化授权表。今后修改这些规则仍需按具体决定及当前授权判断，不能用一个广义“自治”标签覆盖待决定问题。原地回答的真实交互、跨部件转交和并发机制继续由插件负责，并须独立验证。

同插件 `docs/DISPATCH-SIMPLIFICATION-2026-11-06.md` 第 12—17 行还明确区分真实原生组件、夹具模型、隔离真实 Web 宿主与常驻激活。该文件记载的检查不能证明后续真实模型使用或常驻宿主代码已生效。本次读取这些验收说明，没有重新运行其中测试；SSOT 应保留这种观察边界，不能因为文档写了“通过”就扩成所有环境均已验证。

### 已接受不等于已实现，设想不等于已经发生

Calliope 工作边界第 44—57 行解释候选身份，第 101—102 行区分未来设计与正式文本进度。3.15 memory model 第 36—47 行已经区分当前、计划、Agent 推断及观察证据。4.0 延续这些区分，将事实依据从软件代码扩展为相关领域的实际来源：软件行为看代码、配置和运行；用户决定看其原话与正式决定；作品事实看现行事实 owner，文本进展看正式文本；研究结论看材料和方法。

这不让文档凌驾于运行事实，也不让代码替代用户意图。发生冲突时先辨是文档陈旧、实现违反规则，还是决定尚未实现，再修正确的一侧。审美价值和产品推荐仍需显式判断，不被写成客观证明。

### 文档整理必须保住独立知识与资产

Calliope 近期决策文件 `docs/创作示例/02_谁准长明/10_项目控制/04_设计决策历史/2026-11/2026-11-05_01.md` 第 29—43 行记载，前序清理误删已认下资产，随后从 Git 找回，并修复部分覆盖损失。这是项目记录提供的具体失败信号；本次未独立复演其数量和恢复完整性。它足以说明“有历史可找回”和“链接未断”不能替代内容保全。

3.15 bootstrap 的 v2 迁移已有内容逐项保全，普通 closeout 却更强调修正文档和链接。4.0 将保全应用到会损失知识的拆分、合并、压缩和迁移：事前识别独立决定、理由、拒绝方向、范围例外与有价值内容，事后核对去向；不能判断的先保留并明确问题。无需给所有编辑建立永久清单。明确删除授权、真实资产恢复和领域内容核对仍由项目承担。

### 持续工作的状态留在既有工作记录

Calliope `过程资料时序与归属.md` 第 7—9、24—36 行要求研究组保存输入、原返、失败及续接关系，从入口能找到判断及其父稿。`skill优化协议.md` 第 128—142 行要求下一次尝试能够区分原因，已结束的假设分支没有新条件不因换会话重开。其悬案账本还保存用户决定暂缓同步的事项。

3.15 已支持 open questions、研究结论、延期原因和重新查看条件，bootstrap 和 Doctor 也有专用恢复路径。4.0 补齐普通持续工作的阅读边界：按明确任务身份找到项目已有记录，保留已确认决定、已完成部分、阻塞与下一安全动作；不凭“最新文件”猜任务。当前任务状态、调用原件和逐次证据继续由项目记录持有，长期记忆只保存仍指导后续判断的结论、规则、陷阱和入口。

### 机械登记有自己的 owner

`dsh-plugins/docs/followups.md` 第 7—39 行区分待办与“已经做了但仍待真实使用证明”的事项，规定取证方法、复看条件、去留决定与关闭证据，机械检查只判断字段完整。其 `AGENTS.md` 已把这一机制接入日常入口。SSOT 再建同类待验证表只会增加漂移。

4.0 保留并路由项目已有的机械注册、任务系统和研究记录；关闭条件及责任留在原 owner。SSOT 可以解释为何需要它们和什么时候去读，不复制条目。调度、提醒、自动触发和数据校验属于项目能力，不是 skill 文本能保证的结果。

### 验收要观察实际使用表面

`dsh-plugins/docs/plugin-development.md` 第 89—99 行要求按真实风险选择实现与检查，完成声明只覆盖实际运行的层级；`docs/plugin-walkthrough.md` 第 23—44 行区分源码、隔离环境、替身、正式安装和实际加载。Calliope 的过程规则第 36 行也明确：链接与文件名只证明可找，不能证明文学结果或流程收益。

4.0 沿用 Doctor 的新读者任务检查，并使行为主张检查适用于领域资料，不限于寻找代码条件。项目自己的浏览器、实际模型、服务读回和文学判断不能由 SSOT checker 替代。SSOT 接入成功也不能被写成项目功能已通过验收。

### 宿主恢复只是额外的职责边界案例

`deepseek-harness/docs/subsystems/plan.zh.md` 第 5—17 行把软性计划指引、沙箱限制和审批策略分开，也描述日志恢复及尚未持久化选择的边界。这是官方宿主能力的补充案例，不能代表 dsh-personal-agent 自身的产品行为。它说明“Agent 记住了一个决定”与“运行时已经持久化并会恢复它”是两件事。

4.0 不增加自动恢复服务，不承诺取消、重试、幂等或后台续行。SSOT 记录项目已建立的恢复语义、限制和入口；实现缺陷仍由实际 owner 修复，并以相应运行证据判断。

### Git 历史不能替代跨产品会话取证

用户在本轮进一步提出：除了 commit，是否应读取相关 AI 产品中的项目对话来收集决定。这个补充改变了取证范围：Git 只能看到已经落盘的内容，对话里未保存的授权、否决、短回复和后续纠正可能完全不在仓库内。本次读取的是项目文件，尚未跨产品实际读取这些会话，因此不是全对话审计，也不能声称已恢复其未落盘决定。

4.0 新增[会话补记协议](../skills/ssot-doctor/references/conversation-catchup.md)，用于初建、全面补记和用户明确要求跨产品收集时。先盘点相关平台、账户及项目会话，核对项目与任务身份；用搜索和 AI 摘要定位，再读实际问答、用户短回复、必要上下文及后续纠正。AI 的总结和推荐不构成人类确认。全面补记应覆盖声明的可访问相关来源集合，不能静默抽样；缺权限、未连接、不可达或尚未读到的来源与范围必须作为覆盖缺口报告。新增连接不由该协议自动授权。

跨会话推进时，来源 ID、已读范围、旧 thread 追加消息的增量 cursor 与下一安全动作只放在本地 `.ssot-work/`，沿用临时文件的排除提交保护。不能只按会话创建时间查新 thread；旧会话也会追加决定。对应决定完成归位与回读后才能前移 cursor，Git 的 `reviewed_through` 不表示会话覆盖。持久 owner 只存必要原话、问题、日期、范围及来源定位，完整私密对话和无关敏感内容不得提交。这既不建立永久来源覆盖台账，也不要求每个普通任务重读所有产品中的所有会话。

## 为什么选择 4.0 与格式 4

本次改变不只是增补一句建议。3.15 要求不变量解释及持久知识位于 `SSOT/` 内；4.0 允许仓库内已有 owner。如果只改文字而沿用旧格式，旧 agent 或旧 checker 仍可能拒绝外部 owner，甚至在后续维护时把内容搬回。因此选用 4.0 与 `ssot_format: 4`，把新的读取与写入契约显式区分，提供迁移路径。

v3 迁移应原位保留已有知识、ID、来源、确认状态与决定含义；已经在 SSOT 内的内容无需为了证明“支持外部 owner”再次搬走。只有存在明确重复和维护问题、且获得相应授权时才调整归属。接入其他已有文档体系时也先判断 owner，不批量移动。这一选择增加了迁移分支，其收益须由试验和真实接入检验，而不能用版本号证明。

## 建议的取舍与后续准备

本次纳入协议的建议是：仓库内现有 owner 路由、即时保存用户决定及来源范围、接受与实现分离、整理内容保全、工作记录与研究材料分工、复用机械登记、领域证据、v3 原位迁移，以及相关平台项目会话的盘点与实际问答补记。它们替换或澄清已有职责，不能扩展成每次任务都要填的新表。

项目自身继续负责领域事实身份、运行时恢复、调度与提醒、检查脚本、发布与常驻加载验证，以及作品和产品价值判断。已支持的即时落盘、计划标识、延期条件和 Doctor 新读者检查继续使用，不以这次审计名义再建重复机制。对覆盖率、全项目事实一致性、长期成本下降和全部用户诉求完备性，本次不作完成声明。

进入全项目接入前，应先确认目标仓库及工作树、启动入口、现有 owner 和机械登记，再列出预计改动及授权边界。选择正常变更、决定捕获、结构整理、跨会话恢复等真实任务，按[试验记录](../tests/trials-4.0.md)检查候选是否减少错误且没有增加无关读写。实际接入逐项目推进：保留既有资产与来源，先连通最小入口，按任务验证路由与维护，再扩大范围。消费项目本次没有因报告而被修改；后续迁移和接入需要在各自已授权范围内实施。

## CC Sonnet 独立讨论与采纳情况

首轮未采纳“兼容 v3、不升格式号”的建议。回读 3.15 基线 `memory-model.md` 的 inside-SSOT 要求及旧 `ssot-check.py` 第 494—497 行可见：解释放在 SSOT 外会直接报错，并非只有文案风格不同。格式 4 允许原位 owner，旧协议却要求把它迁入内部，形成真实契约冲突；保持 v3 标记会使新旧安装对同一 owner 作相反处理。因此保留 4.0 和格式 4，并要求参与该仓库的安装支持新格式后迁移。这个理由不证明旧安装面对格式 4 会自动安全退出，旧安装行为仍须按试验范围检验，不能把本段代码检查说成已跑过该行为。

后续已将上述基线契约证据交回 Sonnet。其追问回复明确撤回“兼容 v3”的推荐，认可用格式升级标识外置 owner 的契约变化；它说明这一修正依据主会话提供的证据，并非自己运行 checker。讨论因此在保留格式 4 上达成一致，不能只保留首轮分歧，也不能将后来的同意当作独立实验证明。

追问中进一步采纳三项边界：外置 owner 的文件大小、分册和索引按其本地规则，不自动套用 SSOT 新建文件的约 16,000 字符拆分指导；cursor 丢失重扫时同时核对已被取代的决策历史和后续更正，保持历史身份，不能把旧决定重新写成现行选择；带来源的正式决定按项目记录采信，已有 confirmed 不因重新整理而降级，不要求每轮重新证明过去的认可。新的来源不明内容仍保留不确定状态，冲突出现时才处理其具体疑问。

未采纳把适用对象强制增加为所有登记行的新字段并机械检查，也未采纳将每次后续动作都要求新的本轮授权。当前散文明确谁和什么受决定约束，保留现有 owner 足以表达范围，新增全局列会给所有项目增加迁移与维护义务；用户已有授权在适用范围内持续有效，不能因换轮次反复要求确认。产品运行时的决定仍不能自动转授给工作 Agent，范围含糊或出现新冲突时才澄清。适用范围的机器检查可作为未来有实测需求时的可选增强，并非本次已实现能力。中文标题与显式锚点、深层相对路径、JSON 路由及外置超长文件的 checker 实测须以检查记录为准，本段不预先宣布通过。

即时捕获与项目原有同批提交、合并同日迭代并不必然冲突：记录单元和提交粒度继续遵守 owner 规则。分层读取也不等于全面补记可以默默抽样：普通任务按需要读，明确全面补记则读完声明的可访问相关集合，并报告未读与不可达范围。评审提到的项目日期标题、历史本体可达性等，应留给该项目核验，不因本次协议工作擅改消费仓库。

## 后续系统增强与验收边界

下列增强尚未实施，需要独立的产品设计、实现和授权，不能算作本次 skill 已具备的保证。

- **生命周期 hooks。** 由宿主或平台集成在输入、压缩前和结束等实际扩展点提醒或检查未捕获决定，收益是减少完全依赖 Agent 自发识别的漏记。先验证平台支持的 hook、只读任务和无决定任务不写入，再用中断、压缩及后续更正场景测漏捕、误触发和延迟；事件触发本身不能证明决定判断正确。
- **只读多平台 connector。** 由来源适配器提供稳定消息 ID、来源身份、项目归属、分页与脱敏，收益是降低人工导出和来源混淆。用已知完整的合成会话集测试旧 thread 追加、短回复、转发摘要、撤回或编辑、权限不足和分页中断，核对可读范围及零外部写入；账号连接需已有权限或另行授权。
- **持久来源 ID 索引与跨机增量。** 由项目或系统的专用状态存储维护来源边界和幂等对账，收益是减少 `.ssot-work/` 丢失后的重读并支持换机。先决定隐私、存储 owner、同步与保留策略，再用断点前后、重复导入、乱序导出和跨机恢复核对无重复决定、无静默跳过；在此之前只承诺本地临时进度，丢失就重扫并报告不确定覆盖。

这些增强各有自己的状态 owner、权限与验收，不向 SSOT README 复制原始私密对话或永久覆盖台账。即使将来落地，也须分别证明来源可读、身份可信、决定捕获正确和恢复行为成立，不能用连接成功替代全部结果。

## 总体优先级与所有项目接入批次

目标是让所有目标项目都能使用同一套记忆方法；协议适用不等于它们已经完成接入。本轮未执行所有项目扫描、会话导入或消费仓库迁移，以下是接入准备顺序。

1. **先保决定与内容完整性。** 优先验证 owner 路由、即时决定捕获、确认范围、部分更正及整理保全；这些错误可能造成授权误读和不可见的知识损失。跨产品会话协议同时覆盖短回复、旧会话追加和不可达来源，避免把 Git 补记冒充决定全量恢复。
2. **再验证恢复与维护成本。** 在不同资料体系中检查已有工作记录、研究材料和机械登记是否继续各守其职，并记录正常任务的读写成本、漏触发和误触发。协议与 checker 的结构通过后，仍以真实任务试验决定能声明什么。
3. **建立项目与来源清单。** 全项目接入开始时，明确“所有项目”的实际集合、各仓库身份、已有格式、脏工作、指令入口、owner 和可访问会话来源。无法确认的项目或账户留为待确认范围，不凭目录名或最近修改时间推断。
4. **按代表项目试接入，再分批扩展。** 首批选择已有领域 owner、已有 SSOT、已有机械登记等不同形态的项目，验证原位接入和 v3 迁移；每批保留独立验收与回退边界。通过后对其余项目逐批接入，消费仓库的提交和发布遵守各自授权，保护并行工作。
5. **各项目分别补齐会话来源。** 已可访问的相关会话按协议实际读取并归位，缺权限或不可达的单独说明；仓库接入可继续，但不能将该项目的全面会话补记报为完成。完成声明分别列接入、格式迁移、决定补记与实际任务验证，不能合并为一个无范围的覆盖率。

这些批次提供可执行的下一步，并不预设各项目需要相同文件或相同数量的文档。接入完成的标准是目标项目的入口可达、知识仍由正确 owner 持有、已捕获决定保持原意，且声明范围内的实际任务验证有证据；仍有来源缺口时保持明确，不以完成某一批掩盖其余范围。
