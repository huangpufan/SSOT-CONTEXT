# 持续修改的研究和创作项目怎样使用 SSOT

一个方向已经认下，后来仍可能有更好的想法；旧材料值得留着，也可能已经不能照用。SSOT 可以帮助后来加入的人理解这些来由，再继续做具体工作。它保存和路由知识，不替你决定作品好不好，也不把每次讨论变成一套待填表格。

下面用虚构剧院和工艺馆说明现有工作方式。已有的设定、研究、项目控制和决策文件可以继续负责原来的内容，不必搬进新目录；入口只说明去哪里看。这里是使用示例，协议细节仍以链接的 Skill 与 reference 为准，也不会因为这份指南而增加默认读取步骤。

## 先说明项目范围和已有文件的职责

如果你确实需要长期维护，可以对 Agent 说：

> 把这个文件夹作为我们的节目设计 context 空间。简报继续放在原处，研究原件保持原样。先确认入口和读写范围，只补确实缺少的知识，不迁移现有资料，也不要新建统一表单。

[Bootstrap](../skills/ssot-bootstrap/SKILL.md) 会按约定建立或继续入口。普通创作问答不需要先建空间；已有开发仓库继续使用 format 4，不因开始研究而迁移。通用空间如何保留已有目录、权限和多个项目身份，见[空间边界](../skills/ssot-preflight/references/context-spaces.md#entry-boundaries-and-compatibility)。

## 保存认可的理由，只改真正变化的部分

假设剧院简报已有一些待选方向。你说：

> 我认可让观众在人物自己的小成败里感到剧院值得存在，而不是所有人都只替压轴铺路。先试修琴人夺回比赛名次，与旧师傅的争执保留。茶摊只是例子，还没选。把判断和理由留在现有简报，先不写完整剧本。

随后你改变一处：

> 修琴人的目标改为找合奏伙伴，不再以夺回名次为目标；师徒争执和其他已认方向不变。你仍可推荐更好的故事方式，不要把初步采用当永久定案。

此时简报需要让陌生人读懂：观众体验为什么重要，当前角色想做成什么，哪项旧选择被换掉，什么仍成立，哪些例子没有采用。它不应只留下“保持丰富、已确认”几个标签，也不应把整篇旧决定全部作废。[即时记录](../skills/ssot-closeout/references/decision-capture.md)负责保存和读回；[写给陌生读者](../skills/ssot-preflight/references/writing-memory.md)解释应保留多少情境。

新会话可以直接接一个实质任务：

> 评估“所有人物最后都放弃所求，为压轴募款”的提案，给两个可行走向、推荐与代价，再写一段具体场景走向。只交讨论方案，不改已采用事实。

可用的接续应当解释提案为何削弱了已认的体验，正确承接“找伙伴”，仍让师徒争执有作用，并提出能继续讨论的情节。例如，一条路让修琴人学会给新伙伴留位置，另一条路让师徒围绕一次有限试奏谈条件；这都是新建议，不能冒称你已选。记住角色目标只是底线，能用理由作出这样的新判断才体现知识的用处。

多轮修订后，不必让当前说明永远挂满补丁和括号。你可以要求：“按今天仍成立的含义，把这一段通顺重写，保留所有未变的承诺、例外、理由和必要来源；该保留的原话与历史不要删。”局部替换保护的是含义，不是永远保留旧句法；也不授权顺手清理其他资产。

纠偏一端时，原来仍有效的另一端也要留住。例如减少重复错误捕获，不等于撤掉已经约定的外部边界错误提示；让一段关系轻松一些，也不等于把仍成立的冲突全洗掉。沿已有理由说明范围即可，不需要每条要求配成一组对立口号，更不能替你发明新的取舍。

已认方向仍可被挑战。你可以授权沿既定目标改进，或要求先比较再选择；Agent 应沿用现有授权，不重复请示，也不把“可改好”理解成可以自行推翻人类取舍。真正需要长期保护的结果可以登记为规则，临时设定和所有例子不能自动全部升格。详见[保护的范围](../skills/ssot-preflight/references/memory-model.md#5-invariants)。

## 来源坏了，仍可做有边界的判断

工艺馆旧分析声称观众都喜欢一条汇向镇馆宝的路线，但它引用的文件实际是错误网页。获取脚本修好了，并不表示旧文件已重新取得，旧结论也不会自动恢复可信。

你可以要求：

> 核对这个建议依赖的原文，说明目前哪些结论仍有依据。不要改研究原件；用可靠材料给一个可逆的小试方案，并说明什么新证据会改变建议。

如果可靠材料只有三组观察，就只谈这三组。它们可能足以提出小试，却不足以宣布全馆偏好；缺失的资料也不必阻塞完全不依赖它的工作。保存已知限制，让下一位使用结论的人能找到对应来源；重新获取和清洗仍由原研究管线负责。原件、解读和采用如何分开，见[材料的不同含义](../skills/ssot-preflight/references/context-spaces.md#what-the-material-means)。

## 借鉴旧素材，不把旧用法一起带回来

你可以明确保留旧图录供阅读，同时不采用其中某个设计。保留不是恢复现行地位，过时也不等于应当删除。

判断时要看被否的原因。例如，旧“白光”让每位工匠突然知道所有人的意图，抹去了人物差异；“晨辉”若仍做同一件事，改名没有解决问题。但同名“白光”也可能只是十年一次的校镜仪式，不能因名字相同就一律禁用。新方案可以借旧图录的空间灵感，而不继承被否机制。

要求 Agent 解释它借了什么、舍了什么、为什么，比维护一张越来越长的禁词表更能帮助下一次判断。[局部替换](../skills/ssot-closeout/references/decision-capture.md)和[停止使用、替代与删除](../skills/ssot-preflight/references/context-spaces.md#stop-using-supersede-withdraw-or-delete)已有不同处理；没有清理授权就不删素材。

## 允许上游先变，按授权同步下游

例如你说：

> 晚场改为 19:35，日场不变。先改当前时间表。海报和值班表都暂锁，等我发话再同步；旧值不能作为当前到场依据。

之后只开放一部分：

> 现在只解锁值班表，保留原来的日场和无障碍交接。海报继续不动。

记录解锁后，也可以交给新会话的当班负责人执行。正确接续应实际更新值班表、读回结果，并给人可照做的当前安排；旧海报保持原样，同时说明它暂未同步。不能只交一份“将会更新”的计划，也不能为了全局一致擅改海报。如果交接记录本身也未获修改权，应指出哪些表面仍未更新，交给负责该记录且有写权的人依实际文件变化和读回结果对账；只暂缓这部分对账，不自行补权限或新建账本，也不能宣称已经全局同步。若你随后明确把两份都解锁，就应正常完成两份联动，不能把历史冻结当永久规则。

冻结也需要安全的读法。旧值班表的晚场时间暂不能照用，未变的日场和交接规则却仍可依赖；不能因为文件未同步就全盘丢弃。换到创作资料，应向现行权威核对受上游变化影响的设定，把仍有依据、未被替换的人物关系或素材继续用于判断；也可标明假设探索新构思，不冒称旧材料已经重新采用。软件旧模块若真实运行v1，也不能被自动读成v2；历史原件和观测快照仍描述当时发生的事，不能因新决定倒改成新结果。新标准、未迁移的草稿与仍然存在的旧现实，要分别判断。缺少可靠对应关系就保留未知，先做不依赖它的部分，既不暗中换词，也不突破锁定范围。若旧海报仍在现场可见，还应在建议中考虑误到场风险、接应或更正办法，先核对可用人员和授权；文档改好不代表现场已生效，也不授权自动通知或更换实物。

延期的原因和重开条件沿用项目现有的记录位置，不必给每份下游文件新建账本。谁负责当前状态、如何冷恢复，见[延期及已有任务记录](../skills/ssot-preflight/references/memory-layout.md#temporary-workarounds-and-deferrals)。

## 分清已完成的成果与尚未证实的效果

“决定已保存”“新同事据此交出方案”“方案已经实施”和“实际体验变好”是不同事实，不会自动相互证明。写了很多研究，不等于正式作品已完成；正文尚未开始，也可能是你设定了前置质量门槛，不能擅自判作拖延或强迫动笔。

你准备做高成本同步或扩展时，可以先让Agent建议一个相称的小样：一次真实输入、一小段可丢弃试演，或一个实际使用片段，用来暴露设计在目标载体上哪里不顺。这是供你选择的检验办法，不是新的必过门槛；未试不撤销已认决定，也不改变你原来的动笔条件或写入授权。若当前只授权讨论，就先比较小样做法，不自行展开成稿。

入口的例子与细节也可以按用途整理：保留理解本次取舍所需的情境，把只在特定任务才有用的细节留在原文件。必要的反例和被否理由仍须找得到，不能一律删去。是否影响了新的判断，要回到实际产物观察，不能把变短或改成正面措辞直接当作改善。

实际使用后，你可以继续指出：这份分析虽然事实齐全，却像验收报告；或它能帮我找文件，却没有帮助我选择下一场怎么写。这样的反馈应先检查生成和使用方式，再修相关模板、正文或路由，不能只追加一条“注意可读性”。从这类反馈中提炼长期知识时，保留会帮助以后判断的部分；单次运行结果留在本次任务，不变成永久维护日志。这不限制你按现有授权保留经历、原话或其他记录，它们仍由原来的文件维护，不必证明能改变未来决定，见[授权记录](../skills/ssot-preflight/references/context-spaces.md#what-the-material-means)。

检查器负责链接和结构，不能替你验收理解、可用性或审美。[Doctor](../skills/ssot-doctor/SKILL.md)可以针对具体任务检查错误和难用之处；验证到哪一步就说到哪一步。这些例子对应的实际观察与未验证范围，见[本轮评测报告](./open-judgment-2026-11-14.md)。
