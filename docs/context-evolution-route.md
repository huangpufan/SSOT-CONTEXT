# 长期维护项目知识，我们走到哪了？

**当前判断（2026-11-20，正式版 5.13）：已经找到一处可以大幅省力的工作，正在验证它经过多次变更后还能否成立。** 我们希望一个没看过旧聊天的人，用项目自己的文档就能接着做事。他应该能按今天的规则行动，必要时找回昨天为什么那样决定；原文已撤回时，接手也不能把它重新打开。查一次、改一次、等回复、找人确认和做错重来，都算这套办法的成本。[项目目标](../DESIGN.md#accepted-direction-reduce-the-cost-and-friction-of-using-and-maintaining-context)

## 当前阶段与剩余距离

长期探索会随需求继续。为了让进度有分母，本轮选一个能验收的终点：**第一套经过真实项目持续使用、能以更低负担保持可靠交接的做法。** 以下是维护者本次采用的五个阶段判断，覆盖这条降摩擦路线。以前已发布的能力仍算项目积累。

| 到达什么位置 | 当前状态与依据 |
|---|---|
| 1. 能同题比较成本，也能发现“答对却做错” | 已达到。普通文档和 5.13 有同题回执；新接手者拿到的是实际留下的文件。查看文件打开记录，还能发现最终答案掩盖的提前读取。 |
| 2. 找到至少一种值得继续的省法和适用边界 | 已达到。只改一条明确获准的规则，写入加接手从 270,970 降到 66,700 输入 token。建议尚未采纳、缺共同批准两道题，都没有改手册。 |
| 3. 在代表性工作里知道何时用轻量做法、何时需要完整核对 | **进行中。** 单条规则的收益已有样本。轻量更新经过多次替换后能否留下唯一理由仍待检验；读取权限的试验还出现过抢先请求。应分别裁定可用范围。 |
| 4. 在获准的真实项目里跑通采用、观察和回退 | 待验证。此前核对过真实消费者的入口和新会话技能发现。这批省成本的候选仍在隔离试验中，尚无实际采用后的连续任务回执。 |
| 5. 经过后续换班或规则变化，实际总负担仍下降 | 待验证。需要把建库、日常读写、接手和返工按真实发生频率合计，再决定推广、限用或撤回。人的等待和重复解释也要计入。 |

前两项达到，后三项尚未达到。按阶段数是 **2/5（40%），剩 3/5（60%）**。后面三项的工作量和历时未知。75.4% 则是上表第二项里**一次任务的输入降幅**。阶段定义或终点变了，保留旧口径并说明为何改判。[单条更新及权限对照](ordered-lookup-cost.md) · [真实安装与试验边界](context-paths-study.md#安装与验收)

## 哪些积累决定了今天的位置

- **建库与找到入口已有可用改进。** 5.7 减少了两个有现成文档可用的建库案例的调用和消耗。5.5 在大型项目入口把第一次读取缩到标题和文件头，但两道题的整轮输入一升一降。少读一个文件只说明少走了一步。[建库对照](bootstrap-5.7.md) · [大入口实测](large-entry-preflight-2026-11-19.md)
- **普通文档给出参照，复杂历史揭示额外价值。** 另一条三次维护、两人接手的链里，5.13 的维护者比普通文档多用 805,654 输入，两位接手者合计少用 95,079；当前成稿两边都做对，原决定的归属保留程度有差异。实际项目有多少次更新、多少人复用同一份手册，会改变这笔账。[五班交接](read-trigger-study.md#只凭维护后的文件能交出什么)
- **现在最值得区分的是哪种长任务在反复花钱。** 本次从此前 22 阶段的逐项回执重新汇总。七班交接和三班创作合计占 5.13 总输入的 70.2%（Flash，4,208,777 / 5,995,148）和 54.3%（Terra，1,605,953 / 2,957,609）。两组同宿主对照中，5.13 相对普通文档多用输入最多的单步都是展馆第四班：新负责人、新签署记录和修订过的研究材料同时到达。Flash 多用 682,989，Terra 多用 139,986。这选出了一个值得查原因的环节。题目数量由试验设计决定，真实使用频率还需另查。[22 阶段原始汇总](../tests/benchmark/results/context-paths-study.json) · [第四班任务与接手要求](../tests/benchmark/fixtures/six-shifts.json)

## 怎样决定往哪走

**先查反复交接，再决定推广范围。** 第四班实际改了编辑手册和研究任务两份不同职责的文档，已超出单条更新试验的范围。下一步先取同一个第四班前快照，做一对相邻任务：只确认已有手册中的一项改动，以及按原题同时处理任命、版式和研究结论。比较普通文档、5.13 和带轻量分支的做法，看前一题能否直接更新、后一题能否识别需要跨文档核对。先读回写后的文档，再让没见过消息的人交付现行简报、找回被替换决定的作者与理由。之前一份候选曾丢失旧理由；放宽时限再跑又把记录日误当生效顺序。这两种实际出现过的错误都能推翻一次漂亮的节省数字。[第四班及下游成品记录](../tests/benchmark/results/context-paths-study.json) · [已有反例](context-paths-study.md#发行裁决与整组实测)

如果理由在写完时就丢了，改的是写入方法；如果手册保留了理由而新人找不到，改的是接手时的查找路径。如果普通文档同样可靠又更省，就让该类工作直接使用原文档。能跨新任务重复达到“少花且交对”，再决定哪些工作进入真实项目小范围试用。权限问题有独立判断：用正文与摘要各自可能撤回的材料验证实际打开顺序，提前读取就继续限制该读法的使用范围。

**真实任务的分布可以改变优先级。** 在最近的同题样本里，5.13 相对普通文档多用的输入，一次单条改动加接手为 219,576，一次直接查费表为 11,816。约 19 次这样的查表，就能超过一次这样的维护差额。这只是一种敏感性估算。首次获准的真实试点应先从已有任务记录估计查、改、交接的比例，以及等待、确认和返工集中在哪里。如果日常查询贡献更大，就把它提到前面；如果长链的错误开始造成返工，即使它发生得少，也应优先修复。一次局部胜负用于更新这张判断，而后续真实结果可以推翻它。[同题逐次结果](../tests/benchmark/results/ordered-lookup-cost.json)
