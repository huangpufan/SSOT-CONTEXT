# 降低 SSOT 使用和维护成本，走到哪了？

**本仓库已经走完五关中的四关，进度 80%。** 三项真实维护已经交付，接手者也能继续工作。四个执行环节少读了 228.8 万输入 token，但启用和演练就花了 134.1 万，挑材料、审稿和返工也要算。剩下的一关，要看下次真实工作从接单到交付，能否在交对结果的同时连这些开销一起省下来。

截至 2026-11-20，四个环节的输入从 292.9 万降到 64.1 万，降幅 78.1%。正式版仍为 5.13。目标覆盖日常查、改和交接，也包括人的等待与补救。[长期目标](../DESIGN.md#accepted-direction-reduce-the-cost-and-friction-of-using-and-maintaining-context) · [实测与总账](scoped-maintenance-pilot.md)

## 接下来怎样决定

优先处理实际反复出现的问题。试点前一周的 48 条用户消息里，6 条明确问进度、取舍或原因。下一位问进度的人，应能直接从本页得到简短答复。已明确负责人和范围的公开文档，可由当前维护者就地处理；需要受限原件时，仍由负责人提供授权材料。

下一次自然发生的查、改或换班，沿用实际请求记录整轮成本和交付质量。若普通文档同样可靠又更省，该类工作就用普通文档。若选材、返工或等待吃掉节省，就先改最费的环节。只有观察到完整交接正确、总负担下降，第五阶段才算完成。[真实试点记录](scoped-maintenance-pilot.md)

单条费表、跨班历史和多文档换班怎样影响了以上判断，可查[单条规则对照](ordered-lookup-cost.md)、[五班交接](read-trigger-study.md#只凭维护后的文件能交出什么)和[跨领域实测](context-paths-study.md#发行裁决与整组实测)。[试点前后的选题依据](https://github.com/huangpufan/SSOT-CONTEXT/blob/99e5537/docs/context-evolution-route.md)保留了当时的任务权重与取舍。
