# Stage 5 真实会话摩擦与净收益审计（386 个消费会话）

**2026-11-24，基于 `5.16`（`d895753`）现场对 5 个真实在用消费空间近 15 天（2026-11-09 至 2026-11-24）的 386 条纯净消费会话做了只读校准审计。** 此前 `5.14`–`5.16` 与两轮负结果研究均基于合成夹具；本次审计不运行任何收费模型，直接从 Codex 与 Claude Code 原生会话日志核对真实触发率、截断、检查器命中、子 Agent 开销与静默漂移，补齐[长期路线审视](2026-11-20-context-evolution-route.md)第 5 阶段的真实使用证据，并据此重排后续演进顺序。

## 样本范围、口径校准与边界

样本覆盖本机 5 个已接入 `SSOT-CONTEXT` 的活跃消费空间（3 个格式 4 开发仓库：重型插件仓库 A、多模块单仓 B、工具仓库 D；2 个格式 5 通用空间：个人领域空间 C、创作空间 E），时间窗为 2026-11-09 至 2026-11-24。所有消费空间均匿名编号，不包含任何私密正文或本机路径。

初扫得到 415 条日志；经口径校准剔除空会话以及在消费目录启动、实际修改本仓库自身源码的开发会话后，保留 **386 条纯净真实消费会话**（累计原生输入 **17,122,564,220** token 含缓存、**81,607** 次 API 往返、**77,292** 次工具调用）。校准中发现两项极易误判的口径陷阱：一是 Codex 将自动派生的子 Agent 线程与顶层会话存在同一目录，必须按 `session_meta.source` 拆分；二是 Claude Code 含 28 次零工具问答会话，混入分母会严重低估真实改代码时的触发率。分角色校准后的总账如下：

## 五项真实生产发现（合成夹具从未暴露）

1. **指令块 100% 静默漂移：`5.5`、`5.14` 与 `5.16` 零落地。** 现场核查全部 5 个活跃空间的 9 份项目指令文件（`AGENTS.md` / `CLAUDE.md`），虽然其中 4 个空间已用软链接即时指向 `5.16` 源码（第 5 个停在 `5.13` 副本），但 **9/9 份受管指令块均停留在 `5.5` 之前**——不含 `5.5` 的“先读文件头和标题”，不含 `5.14` 的“单文档查询与改写捷径”，也不含 `5.16` 的“技能与入口同一步读取”。原因是安装器升级或软链接前进后不会校验也不协助同步受管块，`ssot-check.py` 也不检查指令块漂移。结果连续三个降本版本从未真正在消费仓库生效。
2. **成熟仓库的巨型入口截断爆发（15 天 1,351 次）。** 合成基准的入口通常只有 3–20 条不变量（2–5 KB），但真实重型仓库 A 的 `SSOT/README.md` 已增长至 **251,182 字节（138,701 字符、366 条不变量）**。因旧指令块缺少按节读取指引，且协议与检查器默认要求所有不变量都留在 `SSOT/README.md` 一张大表内（检查器刻意把不变量行排除在 8,000 字符告警之外），Agent 反复执行 `cat SSOT/README.md`（单次输出 24k–29k token），15 天内在 5 个空间合计触发 **1,351 次入口截断**（其中空间 A 独占 1,188+ 次）和 **1,170 次协议文档截断**。
3. **子 Agent 重复预检与收尾税占全部真实输入的 52.6%。** 211 个 Codex 子 Agent 线程消耗了 **90.12 亿输入 token**（高于全部 160 个人类顶层会话之和）。其中 **192/211（91.0%）** 从头重跑 `ssot-preflight` 并撞上入口截断 **724 次**，**143/211（67.8%）** 重跑 `ssot-closeout`，**62/211** 运行 `ssot-check.py`，而 83 个改动代码的子 Agent 中只有 **10 个（12.0%）** 实际写了 SSOT。现行指令块和 `ssot-preflight/SKILL.md` 把每个子 Agent 都当成冷启动顶层协作者，缺少“父协调者已预检并给清边界时的委托工作路径”。
4. **已观察到的真实正向价值，以及两类真实噪音。** 校准后，全部 **58/58（100%）** 人类改代码会话均在改前读取了 `ssot-preflight` 或入口文档；更重要的是，**`ssot-check.py` 在真实生产中 20 次（Codex 13 次、Claude Code 7 次）拦住了未经新日期来源授权的已确认不变量篡改**，直接兑现了“保护人的决定”这一核心承诺。同时暴露两类高频摩擦：一是检查器在真实会话中报出 **384 次断链错误**，主要源于文档链接了易被清理或未入库的临时验证产物；二是空间 A 的 50 个 Codex 人类会话中，43 次加载了 `ssot-closeout`、32 次跑了 `ssot-check.py`，但最终仅 5 次实际写入 SSOT，另有跨宿主差异待查（Claude Code 空间 A 的 15 个改代码会话中，8 次加载 closeout、0 次写入 SSOT）。
5. **真实消费使用率揭示协议与预算尺错位。** 剔除开发本仓库自身的会话后，全部 386 条真实消费会话对旧版兼容壳（`ssot-audit`、`ssot-skill`）和 `context-source.py`（29.8 KB）的**真实调用均为 0/386**，高频参考文档高度集中在 `memory-model.md`（258 会话）、`batch-closeout.md`（98）、`decision-capture.md`（87）、`writing-memory.md`（63）、`memory-layout.md`（44）与 `context-spaces.md`（21）。与此同时，`5.16` 合并后 [ssot-check.py](../skills/ssot-doctor/assets/scripts/ssot-check.py) 已达 **54,262 / 54,272 字节（仅余 10 字节）**，两份模型根本不会读入上下文的 Python 脚本占去 `skills/` 总预算的 35.5%，而每轮必进上下文的技能目录与适配器块在 CI 中却没有门禁。

基于以上真实分布，工程减负与后续协议研究分为两层推进，不再继续在合成小文档上微调 1–3 KB 文本拆分：

## 2026-11-24 晚间只读校准：Claude Code 归因与首批 9 条 post-5.16 实测

当日完成受管块同步与 `5.16` 落地后，按相同脱敏口径对两项未解问题做了零模型费用只读复核：

1. **修正“Claude Code 空间 A 0/15 写 SSOT”的统计口径缺陷，并定位两项真实事实。** 复查空间 A 近 15 天 66 条 Claude Code 日志（剔除 31 条零工具问答后，共 13 条通过 `Edit`/`Write` 改代码的会话）发现：**实际有 5/13（38.5%）会话通过 `Bash`（`python3` 脚本与 shell 重定向）修改并 `git add` 提交了 `SSOT/` 文档**，且 `ssot-check.py` 在其中 3 条会话真实拦截了已确认不变量修改。此前统计显示为 `0` 是因为初版解析器仅统计了 `Edit`/`Write` 工具对 `SSOT/` 的调用，而空间 A 的 251 KB 巨型 `SSOT/README.md` 超出了 Claude Code `Read`/`Edit` 单次读取上限，迫使 Claude Code 退回 `Bash` 改写 `SSOT/`——这也侧面印证了 `5.17` 主题分片在非 Codex 宿主上的紧迫性。与此同时，仍有 2 条重度改代码会话（分别改 42 处与 82 处并执行 `git commit`）加载了 `ssot-preflight` 却完全跳过了 `ssot-closeout` 与 `ssot-check.py`（另有 2 条未加载预检与收尾），证明仅靠提示词无法保证 100% 收尾检查覆盖。
2. **首批 9 条同步 `5.16` 后的真实 Codex 消费会话（4 条人类顶层 + 5 条派生子 Agent，2026-11-24 15:51–21:56）验证了合批落地与剩余瓶颈。** 全部 **9/9（100%）** 会话在 `AGENTS.md` 同步为 `5.16` 后立刻自动执行了“同一步读取 `ssot-preflight/SKILL.md` 与 `SSOT/README.md`”（协议文档截断在 6/9 会话降至 0），5 条只读子 Agent 的 `ssot-closeout` 触发降至 1/5、`ssot-check.py` 降至 0/5。但两项未闭环瓶颈仍清晰可见：(a) 5/5 子 Agent 仍全部触发 `ssot-preflight` 并各撞上 2–3 次入口截断，核对初始提示布尔标记证实父协调者 5/5 提及了 SSOT 却 **0/5 写清相关保护规则或收尾归属**；(b) 因空间 A 尚未迁移至 `5.17` 分片，2 条重度改代码会话仍触发 42 次入口截断与 25 次 `ssot-check.py` 调用。样本量较小（9 条、单日），仍需分片迁移后持续多周复测。
