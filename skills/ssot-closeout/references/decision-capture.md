# Immediate decision capture

Use this route when visible user input settles a durable choice: confirmation, correction, rejection, or a limit on scope. Discussion-only work can settle a decision; a code diff is not required. An idea still under discussion remains a proposal. Apply closeout's write gates and memory-model ownership rules first; this route grants no authority to migrate an older SSOT, edit another repository, or change protected rules.

1. Read the relevant owner’s own writing, merge, source, index and validation rules first, then its source context. Current human input, a user-supplied export, or an existing source-backed formal project decision can establish provenance; existing confirmed decisions need no repeated origin check or downgrade. A role label or agent summary alone cannot establish a new accepted decision: leave unclear origin candidate or unknown. This route does not override the project’s recording protocol. Preserve the user's words with the question or proposal they answer, the date, and who and what the decision governs (product runtime, repository working agent, or this task), with project and time scope. Product runtime authorization does not authorize a development agent’s external actions. Use a portable source link when appropriate; when a local source link cannot travel, retain the necessary quote and source ID instead. Keep only necessary source context, redact irrelevant private details, and retain project scope. An AI summary is not user acceptance. A bare “yes” without its question cannot establish what was accepted. If the reason was not given, say unknown rather than inventing one.
2. Update that owner now with the smallest sufficient record. Distinguish accepted choice from agent proposal, decision from implementation, and enduring rule from one-time task instruction. Use the README invariant register for lasting rules as memory-model §5 requires; use a decision record only when its consequential-choice threshold applies. Reuse existing decision history or a topic section rather than creating an ADR or log entry for every sentence. Brevity must preserve every distinct constraint, exception, rejection and stated reason.
3. Replace only what the new decision changes. Keep unaffected clauses and their status, link a superseded decision to its successor, and retain historical source context. Apply the memory model's preservation check for reorganization. A correction does not silently revoke other parts of the earlier decision.
4. Save, then reopen the changed passage and compare it with the source before relying on it for dependent work. Check that the question, answer, scope, status, reason and partial replacement survived. Follow the already settled decision without asking again in the same scope; new evidence or a new conflict can require a new decision. Batch closeout later checks this work without duplicating it.

If writing is blocked, report the exact gap and keep the visible decision operative in this session; do not claim it is persisted. A persisted record proves capture, not that implementation exists or future agents will load it. Automatic upkeep depends on loaded instructions, available skills and visible input; it cannot guarantee lossless capture of unseen conversations.
