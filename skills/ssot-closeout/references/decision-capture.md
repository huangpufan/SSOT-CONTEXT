# Immediate decision capture

Use this route when visible user input settles a durable choice: confirmation, correction, rejection, or a limit on scope. Discussion-only work can settle a decision; a code diff is not required. An idea still under discussion remains a proposal. Apply closeout's write gates and memory-model ownership rules first; this route grants no authority to migrate an older SSOT, edit another repository, or change protected rules.

1. Read the relevant owner’s own writing, merge, source, index and validation rules first, then its source context. Establish acceptance and provenance using [human-decision evidence](../../ssot-preflight/references/memory-model.md#human-decision-evidence); this route does not override the project’s recording protocol. For a newly observed user exchange, preserve the user's words with the question or proposal they answer, the date, and who and what the decision governs (product runtime, repository working agent, or this task), with project and time scope. Product runtime authorization does not authorize a development agent’s external actions. Use a portable source link when appropriate; when a local source link cannot travel, retain the necessary quote and source ID instead. Keep only necessary source context, redact irrelevant private details, and retain project scope. If the reason was not given, say unknown rather than inventing one.
2. Update that owner now with the smallest sufficient record. Distinguish accepted choice from agent proposal, decision from implementation, and enduring rule from one-time task instruction. Route [goals and preferences](../../ssot-preflight/references/memory-model.md#goals-and-preferences) by scope and standing. An existing route to the owner suffices. Link an unreachable new owner if authorised, otherwise report the gap. Register a choice only when its source establishes a lasting constraint under memory-model §5; use a decision record only when its consequential-choice threshold applies. When `## Invariants` uses topic shards, put topic-specific rows in the matching shard (with shard-relative `Explained in` links) and cross-cutting rules in the entry. Reuse existing decision history or a topic section rather than creating an ADR or log entry for every sentence. Brevity must preserve every distinct constraint, exception, rejection and stated reason.
3. For a conditional method or default, explain [when it governs](../../ssot-preflight/references/memory-model.md#3-current-planned-and-unknown) in that owner. Replace only what the new decision changes. Keep unaffected clauses and their status, link a superseded decision to its successor, and retain historical source context. Apply the [preservation check](../../ssot-preflight/references/memory-layout.md#preserving-content-when-reorganizing) for reorganization. A correction does not silently revoke other parts of the earlier decision. During capture, reconcile a known task’s now-misleading next step or entry route under [changed guidance](../../ssot-preflight/references/context-tiering.md#reconcile-changed-guidance), even if discussion ends here. Batch closeout handles remaining uses.
4. Save, then reopen from disk before dependent work (you may run the post-write readback in the same tool step right after saving). Compare the saved question, verbatim user words when available, scope, status, reason and partial replacement with the source. For corrections, compare with the pre-edit owner's necessary source excerpts too; preserve their wording within current retention authority and mark the superseded scope. If capture changed the register, routes or other context structure, run `ssot-check.py` before ending this capture, including in a discussion-only turn: use [selected checks](../../ssot-preflight/references/source-retention.md#selected-mechanical-checks) for restricted or uncertain reads, otherwise `python3 <ssot-doctor skill directory>/assets/scripts/ssot-check.py SSOT --since HEAD` (format 4) or `ENTRY` (format 5). Follow the settled decision in scope; new evidence or conflict can require another decision.

If writing is blocked, report the exact gap and keep the visible decision operative in this session; do not claim it is persisted. A persisted record proves capture, not that implementation exists or future agents will load it. Automatic upkeep depends on loaded instructions, available skills and visible input; it cannot guarantee lossless capture of unseen conversations.
