# Batch reconciliation

After the entrypoint's batch comparison, read [writing rules](../../ssot-preflight/references/writing-memory.md) before writing (reuse context); read [layout](../../ssot-preflight/references/memory-layout.md) only when creating or splitting files, writing a decision, research or workaround record, or reorganizing content.

2. **Protect people's rules, then write each change in its single owner.** Before altering a confirmed invariant, protected rule or accepted decision, verify an explicit human decision within the [decider's authority](../../ssot-preflight/references/memory-model.md#human-decision-evidence) meeting memory-model §5; without one, pause only the dependent work, report the conflict and ask instead of recording the new behavior as truth. Update in place using README routes and present tense, preserving accurate unaffected prose and describing an accepted exception within its scope while retaining the rest of the rule and its status. Record a lasting human-established rule or accepted departure as its own confirmed row with dated Source and scope; clauses of an earlier candidate row the user did not discuss stay candidate, and never move a confirmed clause to candidate. Keep register rows concise and put explanations, quotes, and history in the linked owner or cold history; when `## Invariants` uses topic shards, put topic rows in matching shards (shard-relative `Explained in` links), cross-cutting rules in the entry, and retired rows optionally in `invariants/retired.md`. Apply a one-task choice to the requested output, use a decision record only for consequential choices without an owner, and label decided-but-unbuilt behavior as planned. After saving, reopen each changed passage from disk (you may run that readback in the same tool step right after saving) and verify accuracy and cold-reader clarity.
3. **Reconcile what changed.** Follow [changed guidance](../../ssot-preflight/references/context-tiering.md#reconcile-changed-guidance) to keep warm owners consolidated to current behavior (offloading superseded prose, rejected-trial logs, and lengthy verbatim quotes to cold history with a one-line link) and reconcile affected live uses and frozen dependencies. Use its consolidation section when reorganising oversized entries or logs.
4. **Check.** Check new or broader behavior claims, including final summaries, with the writing rules' [claim check](../../ssot-preflight/references/writing-memory.md#checking-behavior-claims), reusing step 2's disk readback when unchanged. Unless this batch stayed outside `SSOT/` and its routed documentation owners (no moved, renamed, or deleted files or linked headings), run the structural checker. Reuse a check that covered the same unchanged result. For restricted or uncertain reads, use [selected checks](../../ssot-preflight/references/source-retention.md#selected-mechanical-checks). Otherwise run `python3 <ssot-doctor skill directory>/assets/scripts/ssot-check.py SSOT --since <commit>` from the batch's starting commit (`HEAD` if nothing is committed yet). Fix errors this batch introduced and those affecting what you wrote. Correct mentions of removed or moved files when they still describe current behavior. Report other errors and the scope checked. Reread any passage edited during step 4 from disk as a newcomer would.
5. **Report.** Carry the checked input conditions into the final response. In your final response, name the canonical documentation owners you changed and why. If you changed nothing, name the owners you compared and say why nothing in them became wrong or missing.

Put SSOT edits in the same commit as the change they describe, if the project's commit rules allow it. Committing and pushing follow the project's existing rules; this skill grants no extra authority.

You are done when every candidate is written to its owner or explicitly judged not durable, changed behavior claims agree with the evidence you checked, and, if step 4 ran the checker, it reports no errors in what this batch wrote. Errors elsewhere are reported, not fixed.
