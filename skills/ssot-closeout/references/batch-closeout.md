Describe an accepted exception within its scope, retaining the rest of the rule and its status. Record a lasting human-established rule or accepted departure from a protected rule as its own confirmed row, with Source and scope established by [human-decision evidence](../../ssot-preflight/references/memory-model.md#human-decision-evidence). Clauses of an earlier candidate row that the user did not discuss stay in a candidate row; never move a clause of a confirmed row to candidate. Put the explanation in the owner the row links to. When `## Invariants` uses topic shards, put topic-specific rows in the matching shard and cross-cutting rules in the entry. Apply a one-task choice to the requested output. A consequential choice without an owner warrants a decision record. Label anything decided but not built as planned.
3. **Reconcile what changed.** Follow [changed guidance](../../ssot-preflight/references/context-tiering.md#reconcile-changed-guidance) for affected current uses, partial historical replacement and frozen dependencies. Use its consolidation section only when reorganising or compressing content.
4. **Protect people's rules.** Changing a confirmed invariant or accepted decision requires an explicit human decision within the [decider’s authority](../../ssot-preflight/references/memory-model.md#human-decision-evidence). Use the applicable decision from this conversation or its established owner. Record it with its date. Without one, pause only the work that depends on the change, and ask. Record a departure from a protected rule as decided only when the approval rule in memory-model §5 is met, as step 2 says; otherwise report the conflict to the user, and do not record the new behavior as the truth.
5. **Check.** Check new or broader behavior claims, including final summaries, with the memory model's [claim check](../../ssot-preflight/references/writing-memory.md#checking-behavior-claims). Unless this batch only edited the contents of files outside `SSOT/` and its routed documentation owners (no file or heading added, moved, renamed, or deleted), run the structural checker. Reuse a check that covered the same unchanged result. For restricted or uncertain reads, use [selected checks](../../ssot-preflight/references/source-retention.md#selected-mechanical-checks). Otherwise run `python3 <ssot-doctor skill directory>/assets/scripts/ssot-check.py SSOT --since <commit>` from the batch's starting commit (`HEAD` if nothing is committed yet). Fix errors this batch introduced and those affecting what you wrote. Correct mentions of removed or moved files when they still describe current behavior. Report other errors and the scope checked. Reread each changed passage as a newcomer would.
6. **Report.** Carry the checked input conditions into the final response. In your final response, name the canonical documentation owners you changed and why. If you changed nothing, name the owners you compared and say why nothing in them became wrong or missing.

Put SSOT edits in the same commit as the change they describe, if the project's commit rules allow it. Committing and pushing follow the project's existing rules; this skill grants no extra authority.

You are done when every candidate is written to its owner or explicitly judged not durable, changed behavior claims agree with the evidence you checked, and, if step 5 ran the checker, it reports no errors in what this batch wrote. Errors elsewhere are reported, not fixed.
